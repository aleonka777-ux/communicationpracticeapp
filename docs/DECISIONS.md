# Decisions — Virtual Communication Coach

Significant technical decisions and the reasoning behind them. Newest at the top.

## Navigation-latency fix: the destination route, not the watchdog, was the ~8.4s cause

Production session `8a16f7c9-29bc-410c-a9c7-612e32a9eaee`: `/api/practice/end` succeeded, `router.push()` was called immediately after, and the browser sat on "Wrapping up…" for 8.464 seconds before the feedback route actually rendered. `navigation_stalled` fired at ~8.402s and `navigation_completed` only 62ms later — tempting to read as "the fallback rescued a stuck navigation," but that was explicitly NOT assumed and instead verified against the actual code.

**1. Reconstructed exactly, from code**: `navigation_started` corresponds to `router.push(`/practice/${sessionId}/feedback`)`, called right after `dispatch({ type: "EVALUATION_COMPLETE" })`. The watchdog (then a standalone `useEffect` gated on `state === "complete"`) armed a plain `setTimeout(8000)`; on firing it did exactly one thing — `logStage("navigation_stalled"); setNavigationStalled(true)` — a UI flag only. The actual hard-navigation fallback (`window.location.assign(...)`) lived ONLY inside a `<Button onClick>` handler — it required an explicit manual click. `navigation_completed` is logged in the mount effect's CLEANUP function, i.e. only when the component genuinely unmounts (React Router swapping in the destination route).

**Conclusion, verified not assumed: the 62ms gap was NOT the fallback.** A human physically noticing new text and clicking a button within 62ms of it rendering is not physically plausible. Since nothing else in the code auto-triggers `window.location.assign`, the only remaining explanation consistent with the code is that the ORIGINAL `router.push()` navigation was already in flight and simply happened to resolve about 8.4 seconds after being called — independent of the watchdog, which just happened to sit slightly earlier on the same clock. This reframes the entire investigation: the watchdog was never the hero here; whatever made the destination route slow is the real target.

**2. Original client navigation**: `router.push()`, as suspected — Next.js's App Router client navigation, which returns `void` and has no completion promise. Confirmed the codebase already (correctly) uses this component's own UNMOUNT as the completion proof, not a timer or a route-pathname watcher — verified this detector is NOT itself the bug: a component only unmounts when React Router genuinely swaps in the destination's component tree, so `navigation_completed`'s timing is trustworthy evidence of when the swap actually happened.

**3. Why the soft navigation took >8 seconds — the destination route's own sequential work.** `src/app/(app)/practice/[sessionId]/feedback/page.tsx` (`export const dynamic = "force-dynamic"`, so every navigation re-executes it fully, no caching) awaited `getSessionWithContext(supabase, sessionId)` and `getEvaluationForSession(supabase, sessionId)` **sequentially**, one full round trip after another, despite `/api/practice/end` having already persisted both rows before `navigation_started` even logged — there is nothing for the second query to legitimately wait on the first for. Layered on top: the wrapping `(app)/layout.tsx` independently performs its OWN `supabase.auth.getUser()` + `getCurrentProfile()` (also `force-dynamic` via cookie-based auth, so this re-runs on every navigation too, even between two pages under the same layout), and the feedback page performs a THIRD `auth.getUser()` call of its own (defense-in-depth, matching this project's established "RLS is defense in depth, not the only check" pattern from `CLAUDE.md` — a legitimate, deliberate check, not removed). None of these individually explains 8.4 seconds under normal conditions, but this is a genuinely long, entirely sequential chain of round trips (middleware auth refresh → layout auth+profile → page auth → page session → page evaluation), and a single slow/cold link anywhere in that chain — plausible right after a long-running WebRTC voice session — is sufficient to produce an outlier this large. Only the ONE clearly, unconditionally unnecessary sequential dependency (`session` then `evaluation`, on the page itself) was fixed; the layout's own auth+profile fetch and the page's own defensive re-auth were NOT touched — removing either is a larger architectural change with security/shared-layout blast radius far beyond a "narrow navigation fix."

**4. Is hard navigation dramatically faster, and why?** Yes, structurally: `window.location.assign()` is a full page load — a fresh HTTP GET/response cycle with no client-side router state to reconcile — while `router.push()` must complete an RSC/Flight request-response round trip AND reconcile it into the existing React tree. Neither is inherently faster in the FIRST-BYTE sense (both ultimately wait on the same server-side rendering work), but a hard navigation is not entangled with the CALLING page's own component lifecycle the way `router.push()` is here — this investigation did not find evidence that hard navigation bypasses the slow server-side work; it only bypasses the (here, irrelevant) client-side router reconciliation step. Per the explicit instruction, routing was NOT wholesale replaced with hard navigation — the actual fix targets the real bottleneck (the destination route's own unnecessary sequential fetches) instead.

**5. UX principle — implemented via the existing route architecture, not new machinery.** The Next.js App Router ALREADY has the "navigate promptly → show a loading state on the destination" mechanism this principle asks for: `(app)/loading.tsx` is a Suspense fallback that Next.js can stream back near-instantly while the page's own async work resolves — no new component needed. What actually starves it is upstream blocking work (layout-level auth) sitting above the Suspense boundary; the fix that's actually in scope here (parallelizing the page's own two reads) directly reduces how long the real content takes to resolve once that boundary is reached, without touching the loading-state architecture itself.

**6. Fallback safety preserved, made more useful, not removed or weakened.** The manual-click-only fallback was upgraded to fire AUTOMATICALLY once the watchdog elapses (still keeping the visible manual button as a backstop) — since `/api/practice/end` has already succeeded by the time this component is even capable of reaching "complete," a hard GET navigation to the already-fully-materialized feedback URL is unconditionally safe to trigger without asking first. Verified, not assumed: `/api/practice/end` (`src/app/api/practice/end/route.ts`) is independently idempotent — it calls `getEvaluationForSession` FIRST and returns the existing evaluation immediately if one is already persisted, before ever calling `runEvaluation`/`saveEvaluation`/`markCompleted` again. The navigation-recovery module extracted for this fix (`src/lib/practice/navigationRecovery.ts`) structurally cannot call `/api/practice/end` at all — its only capabilities are `softNavigate`/`hardNavigate`/`onStalled`, none of which is a fetch/mutation — so the fallback path can never be the source of a duplicate finalization even in principle, independent of the route's own idempotency.

**Fix implemented**:
1. `src/app/(app)/practice/[sessionId]/feedback/page.tsx`: `getSessionWithContext` and `getEvaluationForSession` now run via `Promise.all` instead of sequentially.
2. `src/lib/practice/navigationRecovery.ts` (new): extracted the soft-navigate + injectable-timer watchdog + hard-navigate fallback into one small, pure, directly-testable module (mirroring `bargeIn.ts`'s own injectable-timer pattern). `NAVIGATION_STALL_TIMEOUT_MS` stays 8000 — no evidence here justifies retuning it, only making its recovery action automatic instead of manual-only.
3. `realtime-simulation-client.tsx`: wired through `createNavigationRecovery()` — `.start()` at the exact moment navigation begins, `.cancel()` in the mount effect's unmount cleanup (the same proof-of-completion signal as before, now also responsible for disarming the watchdog). The manual "View feedback" button remains, now documented as a backstop for the (now-automatic) recovery rather than the only way out.

**Migration**: none — purely a client-side navigation-recovery refactor and a Server Component data-fetching reorder; no schema or persisted-shape change.

**Explicitly not touched**: Realtime, VAD, speech-delivery metrics, evaluation content, the response-stall detector/12s watchdog, interruption logic, Phase 4B.

**Tests added**: `navigationRecovery.test.ts` (8 tests) covering the normal case (start → cancel before timeout → nothing fires), a stalling soft navigation (`onStalled` fires at the timeout), the fallback actually navigating exactly once (no double-fire), the structural guarantee that the fallback path cannot reach any finalize/fetch capability, the watchdog being fully cancelled after normal navigation (pending timer count verified), cancel() being idempotent/safe post-fire, and a custom-timeout override. One addition to `finalizationLog.test.ts` documenting the `navigation_completed` stage's `elapsedMs` field, reflecting genuine route completion rather than a timer guess. `/api/practice/end`'s idempotency was audited directly (read, confirmed pre-existing and correct) rather than newly unit-tested — this codebase has no established pattern for testing Route Handlers directly (only their extracted pure logic), and the logic itself was not changed by this fix. Full suite: 271 tests passing (up from 263); typecheck, lint, and production build all clean.

## State-machine race: Thinking shown during audible AI playback

Production session `3e34e98e-9a3e-496e-98dc-b404bd4aa5d1`: the user said an unexpected phrase, the AI responded normally and audibly, but the UI showed "Thinking" the whole time. Explicitly NOT a response stall — confirmed from the same session's own evidence (`unanswered_user_turn_count = 0`, `longest_unanswered_stall_ms = null`, `avg_ai_response_latency_ms ≈ 636ms`), so none of the response-stall-incident machinery (latency pairing, unanswered-turn evidence, the 12s watchdog) is implicated or touched here.

**Audit, verified directly against `connectionState.ts` rather than assumed.** The reported timestamps: `user_turn 9` (101535.4 → 102264.9) and `ai_turn 8` (102218.2 → 110705.0) overlap by 46.7ms — `ai_turn 8` started 682.8ms AFTER `user_turn 9` began, and 46.7ms BEFORE `user_turn 9` ended. Tracing the actual transition table: `user_turn 9`'s `speech_started` fires while state is `thinking` (from the prior turn) → `USER_STARTED_SPEAKING` → `"user_speaking"`. `ai_turn 8` then starts (`output_audio_buffer.started`) while state is still `"user_speaking"` — but the `user_speaking` row in `TRANSITIONS` had **no entry at all for `AI_STARTED_SPEAKING`**, so the dispatch was silently absorbed as a no-op (state stayed `"user_speaking"`). 46.7ms later, `user_turn 9`'s `speech_stopped` fires → `USER_STOPPED_SPEAKING`, and `user_speaking`'s only entry for that event was **unconditional**: `USER_STOPPED_SPEAKING: "thinking"` — with no check of whether AI audio was, in fact, already playing. Result: `"thinking"`, while `ai_turn 8` continued playing audibly for another ~8.4 seconds with no further `AI_STARTED_SPEAKING` event to correct it (it had already fired once, silently dropped). **Confirmed**: this is exactly the class of bug hypothesized, though the precise event order differs from the initial guess — the AI genuinely started speaking WHILE the user's own turn was still in progress (not after it), because `user_turn 8`/`user_turn 9` are almost certainly one real utterance mechanically split by server VAD (they abut with only a 0.5ms gap, the same signature as prior confirmed VAD-segmentation cases in this codebase) — the AI began replying to what its own turn-detection considered a complete prior turn while the user, from her own perspective, was still mid-thought. Per the explicit instruction, VAD/turn-segmentation was NOT changed to address this — the fix is driven directly by raw `speech_started`/`speech_stopped`/`output_audio_buffer.*` events regardless of how they get bucketed into "turns" downstream, so it is correct independent of segmentation.

**The 29.6ms `ai_turn 7`, incidental.** `ai_turn 7` (98686.4 → 98716.0) ends 0.6ms before `user_turn 8` begins (98715.4) — the same near-zero-overlap shape seen in the response-stall incident's 22ms `ai_turn 5`, and resolved the same documented way: `bargeIn.ts`'s existing "AI finished naturally mid-timer → promote to immediate turn start" rule reports `user_turn 8`'s start immediately (no confirmed barge-in), landing cleanly in `"user_speaking"`. This boundary is NOT the cause of the Thinking-during-playback bug — tracing forward, `user_turn 8` itself ends normally (`USER_STOPPED_SPEAKING` while no AI turn is active → correctly `"thinking"`), and the actual race is entirely contained in the `user_turn 9`/`ai_turn 8` boundary described above. It is, however, a data point reinforcing that this session's turn-taking was unusually tightly interleaved (three overlaps/near-misses in quick succession), which is what surfaced the underlying state-machine gap in the first place.

**Fix — resolved from real concurrent evidence, not a timeout.** Two changes to `connectionState.ts`, both gated on actual facts rather than guesses or delays:
1. Added `user_speaking: { AI_STARTED_SPEAKING: "speaking" }` to the static transition table — when the AI genuinely starts producing audio while the user is still mid-turn, the UI reflects that immediately, in real time, rather than waiting for the user's own turn to end.
2. `RealtimeConnectionEvent` gained an optional `aiSpeaking?: boolean` field, used ONLY by `USER_STOPPED_SPEAKING`. `transitionRealtimeConnection()` now special-cases `USER_STOPPED_SPEAKING` while `state === "user_speaking"`: if the caller supplies `aiSpeaking: true` (real evidence, not inferred by the reducer itself), the result is `"speaking"` instead of the table's default `"thinking"`. This covers the case fix #1 does NOT — the AI was already speaking BEFORE the user's current turn began (a genuine barge-in-shaped overlap), so no fresh `AI_STARTED_SPEAKING` ever arrives while in `"user_speaking"` to trigger the new table entry.

The "real evidence" is a new `aiAudioPlayingRef` in `realtime-simulation-client.tsx`, set `true` on `output_audio_buffer.started` and `false` on `.stopped`/`.cleared` — deliberately NOT reusing `bargeIn.ts`'s own internal `aiSpeaking` flag, which is intentionally broader (it also covers the `response.created`-to-`.started` pre-playback window, for the unrelated purpose of echo protection during that gap). Conflating the two would have reintroduced a bug in the opposite direction: showing "Speaking" before any audio was actually audible. The ref is reset to `false` on every reconnect, matching the existing pattern for `bargeInRef`/`micMonitorRef`.

`speaking`'s own transition table gained no new entry (it already had none for `USER_STOPPED_SPEAKING`) — a comment was added clarifying that this is intentional: staying `"speaking"` via the reducer's `?? state` fallback is exactly correct when the user's turn ends while the AI is already confirmed speaking.

**Explicitly not touched, per scope**: Realtime response generation, stall detection, the 12s watchdog, VAD/turn segmentation, interruption metrics, Phase 4A metrics (pause/filler/intensity), the Evaluation Engine. No migration — this is a pure client-side state-machine fix; no schema, no persisted shape changed.

**Tests added** (`realtimeConnectionState.test.ts`, 7 new, in a dedicated `describe` block): (1) the normal case — user stops with no AI turn in flight → thinking → AI starts → speaking, unaffected by this fix; (2) the exact production race reproduced from the real timestamps — AI starts while the user is still mid-turn, then the user stops 46.7ms later, and state is `speaking` throughout, never `thinking`; (3) the reverse order — AI already speaking before the user starts (barge-in-shaped), user stops while AI is still genuinely playing → stays `speaking`; (4) AI stops after the user already stopped → correctly falls to `listening`; (5) a genuinely stalled response (no AI turn at all) still enters and stays in `thinking` exactly as before this fix, confirming the response-stall incident's own machinery is untouched; plus two guard tests confirming the `aiSpeaking` override never fires when evidence says AI is not speaking, and never applies outside `USER_STOPPED_SPEAKING`/`user_speaking`. Full suite: 263 tests passing (up from 256); typecheck, lint, and production build all clean.

## Response-stall incident: "Thinking" stuck ~45s, and a system failure blamed on the user

Production session `c2167057-3c37-4860-b995-def145bc92b5` showed the UI stuck showing "Thinking" for ~43-45 seconds after `user_turn 8` ended, with no AI turn at all until the user eventually spoke again (`user_turn 9`). Independently, `realtime_session_metrics` recorded `longest_user_response_latency_ms = 45152.4` — the stall had been silently attributed to the USER as an unusually slow response, when it was actually a system/infrastructure non-response.

**Part A — lifecycle around the 22ms `ai_turn 5`.** Reconstructed from the reported timestamps against `bargeIn.ts`/`sessionTimeline.ts`'s actual logic (not assumed): `user_turn 7`'s `speech_started` fell inside a still-pending response's confirmation window, producing `confirmed_barge_in` at `84541.7` (≈250ms after `user_turn 7` began, matching `DEFAULT_BARGE_IN_CONFIRM_MS`) — a real, correctly-classified barge-in. `ai_turn 5` (`86807.8 → 86829.8`) is a separate, later response (server `turn_detection.create_response: true` auto-creates a reply once `user_turn 7`'s `speech_stopped` fires) that itself concluded essentially the instant `user_turn 8` began (`86829.4`, 0.4ms before `ai_turn 5`'s own end) — exactly the "AI finished naturally mid-timer → promote to immediate turn start" case documented in `bargeIn.ts`, which is why no second `confirmed_barge_in` row exists there. `sessionTimeline.ts`'s own bookkeeping around this boundary was verified to stay internally consistent — `pendingResponseId`/`currentAiResponseId` are correctly cleared via the same idempotent `closeAiTurn()` every turn uses, so this module's data does not itself get "stuck." **What client-side code cannot prove**: why the *server* never produced a `response.created`/audio for the turn that should have answered `user_turn 8` — that is server/infrastructure-side behavior outside this codebase's visibility. Part F's new instrumentation (below) is aimed at closing exactly this gap on the next reproduction.

**Part B — what "Thinking" means, and why it can stick forever.** Traced `connectionState.ts` directly: `thinking` is entered only via `user_speaking --USER_STOPPED_SPEAKING-->`, and (before this fix) could only be LEFT via `AI_STARTED_SPEAKING` (→ `speaking`) or the user speaking again (`USER_STARTED_SPEAKING` → `user_speaking`). Confirmed from the client's event switch: **`response.done` (regardless of status) and the generic `error` event never dispatched anything to the state machine** — a response that is created and then fails/cancels/times out without ever producing audio left the UI showing "Thinking" with no way out except the user manually speaking again. This is exactly what "she eventually spoke again" reflects at the UI layer.

**Part C — Phase 4A causal audit.** Explicitly verified, not assumed: `micEnergyMonitor.ts`'s `setInterval` callback does no I/O and cannot block the main thread meaningfully; `speechDeliveryTracker.ts`'s `openTurn`/`closeTurn`/`pushEnergySample` are pure, synchronous, allocation-light operations. Nothing in Phase 4A explains the 43-45s gap itself. However, the audit DID find a real, independent gap: `speechDeliveryRef.current?.openTurn(...)`/`closeTurn(...)` sat, unguarded by try/catch, directly between critical `sessionTimeline`/`bargeIn` calls in the hot event-handler path — an exception there (how ever unlikely under current implementation) would have prevented `bargeIn.handleSpeechStarted()`/`handleSpeechStopped()` from ever running for that event. Fixed regardless of whether it caused this specific incident, per the explicit "analytics MUST be non-blocking and failure-isolated" requirement: extracted a small `safeCall()` helper (`src/lib/realtime/safeCall.ts`) and routed all three Phase 4A call sites (`openTurn`, `closeTurn`, `pushEnergySample`) through it, each with its own error-logging callback. This makes the isolation guarantee itself directly unit-tested, not just an inline pattern trusted by inspection.

**Part D — the latency-pairing bug, confirmed exactly.** `sessionTimeline.ts`'s previous algorithm computed, independently for each confirmed user turn, "the most recent AI turn ending at or before this turn's start" — with no bound on how far back that search could reach. `ai_turn 5` ended 0.4ms after `user_turn 8` began, so the overlap check correctly refused that pairing — but the algorithm then moved on to `user_turn 9` (spoken ~45s later) and paired IT with the same stale `ai_turn 5`, since nothing prevented scanning arbitrarily far forward for a later turn that happened to satisfy "no overlap." `user_turn 8` itself was silently skipped. Verified precisely: `131982.2 - 86829.8 = 45152.4`, the exact reported value. **Fixed** by replacing both `avgUserResponseLatencyMs`/`avgAiResponseLatencyMs` (and median/longest) with a single merged, chronologically-ordered timeline of every AI turn and confirmed user turn, walking only STRICTLY ADJACENT pairs — never scanning further back or skipping forward. An adjacent-but-overlapping pair (the `ai_turn 5`/`user_turn 8` case) now correctly produces NO latency value (missing, not reassigned elsewhere) rather than manufacturing a number; a later, non-adjacent turn can never inherit an older turn's latency, because adjacency in the merged timeline is now the only thing that produces a value at all. Reproduced the EXACT production shape (all reported timestamps) in a regression test — `snapshot.session.longestUserResponseLatencyMs` is `1120.8` (correctly paired against `ai_turn 4`), never `45152.4`.

**Part E — representing the stall itself.** New, explicitly non-coaching evidence: `UnansweredUserTurnMetric` (`sessionTimeline.ts`) — a confirmed user turn whose immediate successor in the merged timeline is a LATER user turn (no AI turn occurred between them at all) or nothing (session ended), beyond `MIN_UNANSWERED_GAP_MS = 2000` (10x+ above the ~150-200ms gaps observed for ordinary VAD-segmented continuations of one utterance, far below any real stall — see the constant's own doc comment). Session-level `unansweredUserTurnCount`/`longestUnansweredStallMs` round out the evidence. Deliberately the SMALLEST reliable representation: a count + longest duration + per-occurrence list, not a new coaching metric, not an attempt to fully classify every failure sub-mode (no-response vs. cancelled vs. failed vs. created-but-no-audio) at this persisted layer — that finer distinction is what Part F's live diagnostics are for, since they see the moment-by-moment event stream Part E's finalize()-time reconstruction cannot.

**Part F — instrumentation.** `debugLog.ts`'s `logRealtimeDebugEvent` now REQUIRES a `sessionElapsedMs` parameter (previously an inconsistent, optional `extra` field on some call sites only, with wall-clock `ts` as the only guaranteed timestamp) — every debug line is now directly comparable to `realtime_turn_events` timestamps. Added coverage for every step in the requested lifecycle list: `response_create_sent` (both explicit sends — the opening line and the text-fallback path — previously unlogged entirely), `automatic_response_expected` (logged on every `speech_stopped`, since `turn_detection.create_response: true` means the server — not this client — is expected to auto-create a reply; makes the ABSENCE of a subsequent `ai_response_created` visible for the first time), `first_output_audio_delta` (new `response.output_audio.delta` case, logged once per response id via `respondedWithFirstDeltaRef`, confirmed as the real Realtime SDK event name from `node_modules/openai/resources/realtime/realtime.d.ts`), `output_audio_buffer_clear_sent` (split out from the existing `response_cancelled` log into its own event), and `realtime_error` (the generic `error` case is now ALSO routed through the structured debug stream with `uiState`, not just `console.error`). `ai_response_created`/`ai_response_done` now include the actual `responseId`/`status`. Together these let a future reproduction distinguish "no response created" / "response created but no output" / "output generated but playback never started" purely from this log stream.

**Part G — watchdog/recovery, two complementary mechanisms, no blind retry.** Audited what current Realtime semantics actually prove: there is no state-query capability over this WebRTC data channel to ask "is a response still active?", so unconditionally sending a fresh `response.create` risks a duplicate/overlapping AI reply if a merely-slow response later resolves on its own — explicitly rejected per "no arbitrary retry implementation without lifecycle proof." Two mechanisms were implemented instead, each gated on an actual proof condition:
1. **Lifecycle-proven recovery** (`connectionState.ts` + the `response.done` handler): added exactly one new transition, `thinking --AI_FINISHED_SPEAKING--> listening`, dispatched only when the client is still `thinking` AND a `response.done` arrives for that wait with `status !== "completed"` — i.e., the server has DEFINITIVELY told us this specific response produced no audio. This is not a retry (no `response.create` is sent); it only corrects the UI to match a proven fact instead of continuing to claim "Thinking" about a response that has already, provably, ended.
2. **Watchdog timer** (`THINKING_STALL_TIMEOUT_MS = 12000`, ~20x the ~600ms median AI response latency measured in production, comfortably below the ~43-45s incident) — covers the case mechanism 1 cannot: a TRUE silence where no `response.done` (or anything else) ever arrives at all, which is what the actual production incident looks like from the client's perspective. On firing, it only reveals the existing "type instead" text fallback and an explanatory notice, and logs `thinking_stall_detected` — a recovery AFFORDANCE the human acts on, never an automatic duplicate-inducing action.

**Migration**: `0015_response_stall_evidence.sql` — two new additive columns on `realtime_session_metrics` (`unanswered_user_turn_count`, `longest_unanswered_stall_ms`) for Part E's evidence. The latency-pairing fix itself (Part D) needed no schema change — `avg/median/longest_user_response_latency_ms` already had the correct intended semantics; they were simply computed incorrectly.

**Explicitly not touched**: VAD thresholds, `MIN_INTRA_PAUSE_MS`, the adaptive noise-floor algorithm, WPM calculation, filler-candidate logic, intensity semantics, the Evaluation Engine, feedback, `VOCAL_EVIDENCE_AVAILABLE`. No Phase 4B work started.

**Tests added**: `realtimeConnectionState.test.ts` (the new `thinking`→`listening` transition), `safeCall.test.ts` (4 tests proving the failure-isolation helper itself), `debugLog.test.ts` (updated for the required `sessionElapsedMs` parameter), and `sessionTimeline.test.ts` (3 new tests: ordinary adjacent-pair latency: the exact production incident reproduced end-to-end from its real timestamps, proving `longestUserResponseLatencyMs` is never `45152.4` and is correctly `1120.8`, that the stall is captured as one `unansweredUserTurns` entry, and that the legitimate `user_turn 6`/`7` VAD-segmentation is NOT misreported as a stall; and a cancelled/pre-playback-response case proving a phantom-free cancelled response never confuses adjacency pairing). Full suite: 256 tests passing (up from 248); typecheck, lint, and production build all clean.

## Phase 4A pause timestamp clock-origin fix

The first production Phase 4A dataset (`session_id = 7b7ad9d0-6290-4fe2-893d-c1c2346e20fa`) showed every one of 10 `realtime_pause_events.start_ms` values landing far outside their owning user turn's `[start_ms, end_ms]` span in `realtime_turn_events` — e.g. a pause at `77270.3` attributed to a turn spanning `27621.7 -> 31001.6`. The user's own diagnostic reconstruction found a near-constant `+48831.3ms` offset across all 10 rows; subtracting it placed every pause correctly inside its turn, and `position_ratio` was already consistent with the turn once that offset was removed.

**Root cause, verified directly from code (not assumed):** `sessionTimeline.ts` establishes its own session-relative zero point at construction — `sessionStartMs = now()` captured once, with every subsequent value being `elapsed() = now() - sessionStartMs`. `speechDeliveryTracker.ts` had NO equivalent anchoring: `const now = options.now ?? (() => performance.now())` was used to timestamp `openTurn`/`closeTurn`/pause events DIRECTLY, with no subtraction of any start-of-tracking reference. `micEnergyMonitor.ts` was audited too and ruled out as a contributor — it never produces or passes a timestamp at all (only a scalar RMS float per tick), so `AudioContext.currentTime` was never in the picture; the mixed clocks were **raw, un-anchored `performance.now()` (speechDeliveryTracker.ts) vs. `sessionTimeline.ts`'s own session-relative `elapsed()`**, not an AudioContext-vs-performance.now() mismatch as originally hypothesized.

**Why the offset was ~48831.3ms, specifically:** `performance.now()`'s origin is the page's navigation start, not "when this practice session began." `realtime-simulation-client.tsx` constructs `createSessionTimeline()` and `createSpeechDeliveryTracker()` back-to-back in the same mount effect — `sessionTimeline` correctly captures "how long the page had already been running" as its own `sessionStartMs` and subtracts it from everything going forward; `speechDeliveryTracker` did not, so it persisted "ms since page navigation" directly. The gap between the two is exactly how long the page/tab had already been open (browsing home, scenario selection, setup) before the user reached the practice screen — in this production session, ~48.8 seconds. This also explains why it was a single CONSTANT offset across all 10 pauses in one session: both trackers are constructed once, synchronously, at the same moment, so the (missing) anchor is one fixed value for the whole session.

**Pause duration and `position_ratio` were already correct**, confirmed by inspecting the code: `durationMs` is always a DIFFERENCE of two raw-clock reads (`t - turn.silenceStartMs`), and `position_ratio` is a ratio of two such differences (`(raw.startMs - turn.startMs) / durationMs`) — a constant additive offset cancels out of both. Only the absolute `start_ms` value was wrong, exactly matching the user's own diagnostic conclusion.

**Fix — the clock-origin architecture, not a subtraction of the observed offset:** `speechDeliveryTracker.ts` now captures `sessionStartMs = rawNow()` once at construction and redefines its internal `now = () => rawNow() - sessionStartMs`, mirroring `sessionTimeline.ts`'s own idiom exactly. Every existing call site (`openTurn`, `closeTurn`, `pushEnergySample`) already called `now()` and needed no further change. No hardcoded `48831.3` (or any other magic number) appears anywhere — a session starting at a page-navigation-time of 5 seconds, 5 minutes, or 48831.3ms all now produce correctly zeroed, session-relative pause timestamps, because the fix addresses the missing anchor itself rather than the one observed symptom value. Since both trackers are still constructed synchronously back-to-back, the residual skew between their two independent anchors is sub-millisecond — negligible next to this module's own already-documented ~50ms sampling resolution.

**New invariant checks, added to `mergeSpeechDeliveryEvidence.ts`** (where pause evidence, sessionTimeline's turn boundaries, and the session's total duration are all available together): `validatePauseClockOrigin()` checks, per pause, that `start_ms >= 0`; `start_ms <= total_duration_ms`; `start_ms + duration_ms <= total_duration_ms` within a documented tolerance (`CLOCK_ALIGNMENT_TOLERANCE_MS = 2 × DEFAULT_SAMPLE_INTERVAL_MS = 100ms` — twice the tracker's own sampling resolution, to absorb ordinary sample-boundary rounding plus the sub-ms cross-tracker construction skew); that the pause's `start_ms` falls within its owning (sessionTimeline) turn's `[start_ms, end_ms]` span within that same tolerance; and that `position_ratio` is consistent with a ratio recomputed from the pause's own canonical `start_ms` and the turn's canonical span (`POSITION_RATIO_TOLERANCE = 0.02`). No `supabase db push` needed for this fix. Existing production rows for the reported session are left as-is (test evidence, per the task's own framing) — not backfilled.

## Phase 4A: speech-delivery evidence (speaking rate, intra-utterance pauses, filler/disfluency candidates, relative vocal intensity)

The Realtime timing/interruption layer (all entries below) is now stable. This phase adds a second, separate measurement layer collecting objective speech-DELIVERY evidence — for later interpretation by a Communication Manual methodology (Phase 4B, not started), never scored or interpreted here. The guiding product principle carried through every design choice below: **a metric is not automatically a judgment** — a 1.5s pause is neutral evidence until context (what preceded it, what followed it) is available to interpret it, so this phase preserves that context rather than collapsing it into a single number.

**Audit performed first, before any implementation** (full results given to the user in chat; summarized here for the record):
1. **Transcription**: the Realtime session (`src/lib/realtime/session.ts`) hardcodes `input_audio_transcription: { model: "whisper-1" }`, no `prompt` field. Only the terminal `.completed`/`.failed` events are consumed (final `transcript` string + `item_id`) — **no word-level or per-segment timestamps are exposed by the Realtime API for this**, regardless of model choice.
2. **Disfluency reliability**: Whisper-family models (including `whisper-1`) are trained toward fluent, clean output and are well-established to inconsistently smooth over or drop short interjections (`um`, `uh`) and false starts — inherent model behavior, not a bug in this app, and not something a config change here can fix. No verbatim/disfluency-preserving mode exists for `whisper-1` via the Realtime API.
3. **No app-side normalization**: only `.trim()` is applied (client and server) between the Realtime event and persistence — whatever the model emits reaches storage unmodified. The reliability gap is entirely in the model, not in this codebase's own text handling.
4. **Mic constraints** (`webrtcClient.ts`'s `MIC_AUDIO_CONSTRAINTS`): `echoCancellation`, `noiseSuppression`, `autoGainControl` all `true`. `autoGainControl` continuously renormalizes input gain, so **raw amplitude is not comparable across turns/sessions/devices** — only within-turn/within-session relative measures are honest.
5. **No existing Web Audio API usage** anywhere in the codebase (confirmed by full-codebase search) — Phase 4A is the first thing to touch `AudioContext`/`AnalyserNode`.

**Decision: do not switch the transcription model this phase.** Per the explicit instruction not to switch blindly, and because there is no way to empirically verify a better option from this environment (no live API testing here), vocal-disfluency evidence is deliberately treated as best-effort/undercount-only rather than triggering a model change. If this needs closing later, evaluate `gpt-4o-transcribe`'s `prompt` steerability empirically against real production transcripts first.

**Speaking rate (WPM)** — computed inside `sessionTimeline.ts` at `finalize()`, from data it already has (a confirmed turn's final transcript + duration), no new event source needed. `wordCount` is a literal whitespace tokenization (`trim().split(/\s+/)`), not linguistic segmentation — documented as an approximation. `MIN_WORDS_FOR_RATE = 3`: a 1-2 word turn's "rate" is dominated by turn-boundary VAD timing noise (the server's own silence-detection tail baked into every turn boundary), not real articulation speed, so no rate is manufactured below this floor — the turn itself is still recorded, just without a rate. Session aggregates (avg/median/fastest/slowest) are drawn only from turns meeting this floor. A WPM trend (`wpmTrendSlopePerTurn`, simple linear-regression slope of WPM against turn order) is computed only with ≥3 qualifying turns — reported as sign/magnitude only, never labeled "improving"/"declining". No "ideal" WPM is defined anywhere.

**Filler/disfluency candidates** (`src/lib/realtime/fillerCandidates.ts`, pure/no-DOM, called from `sessionTimeline.ts`'s `finalize()` over confirmed turns' transcripts only) — deliberately produces CANDIDATES, never judgments, per the explicit "a word is not automatically a filler" requirement ("It looks like a good solution" — semantic; "Do you know when the meeting starts?" — semantic). Three categories, with explicitly different reliability:
- `vocal_disfluency_candidate` (uh/um/erm/hmm/mmm) — best-effort, UNDERCOUNT-ONLY, per the transcription audit above. Presence in text is reasonable evidence it was said; absence is NOT evidence it wasn't.
- `lexical_discourse_candidate` (like, well, you know, so, actually, basically, I mean, kind of, sort of) — more reliable, since real content words survive Whisper's disfluency-smoothing the same as any other word.
- `repetition_candidate` (immediate word repetition, e.g. "I I think") — reliable independent of the above, for the same reason.

Every candidate is persisted with `classification: "unclassified"` (a zod `z.literal`, not the general enum — enforced at the schema level, not just by convention) plus transcript-relative character position and a short surrounding-context snippet, so a future Phase 4B contextual pass can classify it without needing to re-fetch the transcript. `approxSessionMs` is an explicit proportional interpolation across the turn's own span (position-in-transcript-string × turn duration) — clearly documented as an ESTIMATE, not a measured timestamp, since no word-level timing exists. Self-restarts/abandoned phrases beyond simple immediate repetition are NOT implemented — reliably detecting them would need punctuation/disfluency cues the transcription pipeline doesn't consistently provide; this limitation is documented rather than faked.

**Intra-utterance pauses and relative vocal intensity** — the two evidence types that DO need live audio, since server VAD turn boundaries only delimit whole turns, not silence within one. New pure, fully unit-tested `src/lib/realtime/speechDeliveryTracker.ts` consumes a stream of scalar RMS energy samples (never raw audio) and runs a small state machine per open user turn:
- **Adaptive per-session noise floor**, not a fixed absolute amplitude — different microphones/rooms have very different noise floors, and `autoGainControl` continuously changes the input gain, so no single absolute threshold could be meaningful across sessions/devices. Fast-attack/slow-release tracker (drops instantly to a new quieter minimum; rises only slowly so it doesn't chase speech energy upward). A sample counts as speech once it clears `noiseFloor × 3`, with a hard absolute minimum floor so a near-silent room can't trivially satisfy the multiplier via electrical noise.
- **`MIN_INTRA_PAUSE_MS = 250`**, not arbitrary: ordinary phonetic micro-gaps between syllables/words are well under 200ms; psycholinguistic pause research (e.g. Goldman-Eisler's hesitation-pause studies) conventionally treats silences ≥~250ms as a measurable "silent pause" distinct from normal articulatory transitions. Also comfortably above the tracker's own ~50ms sampling resolution (`DEFAULT_SAMPLE_INTERVAL_MS`), so a genuine threshold-crossing isn't a sampling-granularity artifact. Precision is explicitly bounded to roughly one sample interval — never claimed as true millisecond precision.
- A pause still open exactly at the turn's own boundary (`speech_stopped`) is deliberately EXCLUDED, not reported as trailing — OpenAI's server VAD already waits `silence_duration_ms` (default 500ms) before emitting `speech_stopped`, so trailing silence there is that detection tail, not a pause the user resumed speaking after.
- Position within the turn (`positionRatio` 0–1, bucketed beginning/middle/end) is computed once the turn closes and its true duration is known — deliberately preserved as *evidence of where*, not *whether it was good or bad*, per the product principle above (a 1.8s pause after an aggressive AI statement and a 1.8s pause mid-sentence are structurally different events; this phase records enough to distinguish them later without deciding which is which now).
- Relative intensity (avg/peak/population-stddev-as-"variability" per turn) is computed from the same sample stream, discarded per-turn immediately after aggregation — never persisted as a raw array. Explicitly never called dB/SPL anywhere (code, schema, comments) — this deployment has no calibrated measurement hardware, and `AnalyserNode`'s time-domain samples are inherently relative/unitless, upstream of the browser's own AGC. Only within-turn/within-session comparisons are made; no cross-session "you spoke X% louder than yesterday" claim is possible or attempted.

The thin browser-only wrapper (`src/lib/realtime/micEnergyMonitor.ts`, unit-tested against stubbed Web Audio globals) attaches to the **local mic stream only** (never the remote AI audio) and connects the source to the analyser only — never to `audioContext.destination`, so the user is never made to hear their own mic played back. A single `Float32Array` scratch buffer is reused every tick and reduced to one RMS float before anything reaches the tracker; no sample array ever leaves this function. `webrtcClient.ts`'s `RealtimeConnection` now also exposes `localStream` (the exact same stream already sent to the peer connection) so the client component can attach this monitor — nothing new is captured by exposing it.

**Merging the two independent evidence sources**: `sessionTimeline.ts` (transcript-derived: WPM, filler candidates) and `speechDeliveryTracker.ts` (audio-derived: pauses, intensity) are two separate trackers with two separate lifecycles — the former needs only the final transcript + duration already known once a turn closes; the latter needs live sampling that only exists while the WebRTC connection is open. A new pure, unit-tested `src/lib/realtime/mergeSpeechDeliveryEvidence.ts` combines their two `finalize()` snapshots by `itemId` into the shape posted to `/api/simulation/realtime/metrics`, and is where the accuracy safeguard lives: pause/intensity evidence is filtered to CONFIRMED user turns only (matching the same exclusion the timing layer already applies elsewhere) — a suspected-noise event (likely echo) was never established as real speech, so a pause the analyser happened to observe during one must not be reported as delivery evidence.

**Accuracy safeguards, restated explicitly**: analytics failures never break the live conversation, transcript, or evaluation — the mic-energy monitor starts inside its own try/catch (a failure only means missing evidence for that connection, not a broken call), and the entire Phase 4A payload rides inside the same outer try/catch that already isolates the timing-metrics POST from `/api/practice/end`. Reconnects reset the mic monitor exactly like `bargeInRef` already resets its own controller, so a stale monitor from an abandoned connection can never keep feeding samples into the session-spanning tracker.

**Schema**: new additive migration `0014_speech_delivery_evidence.sql`. Five new nullable scalar columns on `realtime_turn_events` (user_turn rows only: `word_count`, `speaking_rate_wpm`, `avg_relative_intensity`, `peak_relative_intensity`, `intensity_variability`) — extending the existing per-turn event table rather than a new one, since these are the same stable-scalar nature as `duration_ms` already there. Two new tables for variable-cardinality evidence: `realtime_pause_events` (one row per detected pause) and `realtime_disfluency_candidates` (one row per candidate occurrence, `classification` DB-constrained to `'unclassified'` today — the column exists so Phase 4B can widen the constraint and update rows in place later, rather than needing a new table). New session-level aggregate columns on `realtime_session_metrics`, matching that table's existing stable-scalar-aggregate pattern. Both new tables get the same owner-via-`practice_sessions` RLS policies (select/insert/delete) as `realtime_turn_events`. No existing migration was modified.

**No raw audio persisted, anywhere** — not mic buffers, PCM arrays, waveform samples, `MediaRecorder` blobs, base64 audio, or audio files. Only derived scalars (counts, rates, durations, position ratios, relative-intensity floats) and already-elsewhere-persisted transcript text/short context snippets are ever sent to the server. Asserted directly in `speechDeliveryTracker.test.ts` (no `Float32Array`/`ArrayBuffer` anywhere in a finalized snapshot) and re-verified against `sessionTimeline.test.ts`'s existing key-allowlist privacy test (extended with the new field names).

**Debug/QA visibility only**: a new `src/lib/realtime/speechDeliveryDebug.ts` formats per-turn evidence (duration, words, rate, pauses with position, filler candidates with context, relative intensity) to `console.debug`, matching the product spec's example format — dev/QA use only, no production UI, exactly like the existing `formatSessionTimelineDebugLines`.

**Explicitly not done this phase, per the phase's own scope**: no classification of any pause/candidate as strategic/hesitant/reflective/awkward/filler; no scoring; no "ideal" WPM or intensity; no cross-session loudness comparisons; `VOCAL_EVIDENCE_AVAILABLE` stays `false` (unchanged, still gates the Evaluation Engine's paralinguistic-claim guardrail — see `src/lib/coaching/evidenceIntegrity.ts`); no Communication Manual integration; no Admin Panel/User Profile/payments/emotion-analysis work.

**Tests added**: `fillerCandidates.test.ts` (11), `speechDeliveryTracker.test.ts` (10, pause detection/threshold/position-bucketing/intensity/no-raw-audio), `mergeSpeechDeliveryEvidence.test.ts` (5), `micEnergyMonitor.test.ts` (3, stubbed Web Audio — wiring/no-destination-connection/scalar-only-callback/stop-behavior), plus new cases in `sessionTimeline.test.ts` (WPM computation, suspected-noise exclusion, short-turn-no-rate, trend-slope gating, filler-candidate attribution/exclusion, candidate rates) and `realtimeMetricsPayload.test.ts` (schema acceptance/rejection for pauses and filler candidates, mapping fidelity), and one addition to `webrtcClient.test.ts` (`localStream` exposure). ## Realtime timing metrics: AI audible-end is a proxy, not an exact measurement — investigated, no fix applied

A production control session with one deliberate, clear mid-speech interruption was inspected row-by-row (raw `realtime_turn_events`, not aggregates) to check whether a `confirmed_barge_in` near the AI-turn/user-turn boundary at `AI end 20444.0` / `user start 20443.6` was being misclassified — the computed ~0.4ms "overlap" there is correctly filtered by `MIN_MEANINGFUL_OVERLAP_MS`, but didn't match the user's subjective experience of clearly talking over the AI.

**Finding: no confirmed barge-in ever fired for that boundary, and that's correct given the data available.** Tracing `bargeIn.ts`: the user's `speech_started` (20443.6) arrives 0.4ms before the AI turn's own stop event (20444.0). A confirmation timer starts since `aiSpeaking` was still `true` at that instant, but the AI's stop event fires immediately after, and the existing "AI finished naturally mid-timer → promote to immediate turn start" rule cancels the pending timer and calls `onImmediateSpeechStart()` instead of ever reaching `onConfirmedBargeIn()`. This is pre-existing, intentional logic operating correctly on what the data channel reported: per that transport, the AI's turn had just concluded essentially simultaneously with the user starting to speak, so it was — correctly, given only that signal — treated as ordinary turn-taking rather than a barge-in.

**The deeper, now-documented limitation: `output_audio_buffer.stopped`/`.cleared` is a server-side buffer-drain signal, not a guarantee of what the user actually heard.** Per the Realtime API's own documented semantics, `.stopped` fires when the output buffer "has been completely drained on the server, and no more audio is forthcoming" — it says nothing about the client's own WebRTC receive pipeline. WebRTC receivers maintain jitter buffers to absorb network variance; audio already buffered client-side when `.stopped` arrives can keep rendering for some additional, network-dependent interval afterward. This is a structural property of any WebRTC receiver, not a bug in this implementation. So the AI turn's recorded `endMs` should be understood as **a lower bound on / proxy for true audible end, not an exact measurement of it** — and the true audible tail of AI turn 2 plausibly extended past 20444.0, which would explain the gap between the recorded near-zero overlap and the user's clear subjective experience of interrupting.

**No reliable per-response browser playback-end signal exists with the current architecture.** Re-confirmed (consistent with the prior audit below): the remote `<audio>` element carries one continuous `MediaStream` reused for the entire session (`webrtcClient.ts`'s single `pc.ontrack`, `realtime-simulation-client.tsx`'s single `srcObject` assignment), so its `playing`/`waiting`/`pause`/`ended` events reflect connection-level buffering health, not per-response silence boundaries. The only signal that could offer a real per-response tail estimate is `RTCRtpReceiver.getStats()` (`jitterBufferDelay`, `estimatedPlayoutTimestamp`) — connection-level aggregate data, not currently instrumented, and adding it would be new analytics.

**Decision: no code, schema, metric, VAD, or behavioral change this round.** A compensating end-side tolerance (symmetric to the start-side `MEDIA_DATA_CHANNEL_SKEW_TOLERANCE_MS` fix below) was considered and deliberately rejected: that fix was justified because it reconciled two control-plane signals *about the same transport event* within a small, reasoned skew window. This is different in kind — the true unknown is real, network-dependent client jitter-buffer depth, for which this deployment has no empirical data. Picking a padding value without that data would be exactly the arbitrary guess this investigation was asked not to make, and risks reintroducing the opposite failure (misclassifying genuine pre-playback cancellations as audible). Current interruption/overlap metrics carry this known boundary limitation as a result: an interruption occurring very close to an AI turn's recorded end may under-measure or miss overlap that was, in reality, audible.

**If greater precision is needed later**: instrument `RTCRtpReceiver.getStats()` to collect real jitter-buffer-delay data across production sessions first, and only then decide whether — and by how much — to adjust end-of-turn semantics. Never choose a compensating constant before that data exists.

**Also inspected, left unchanged**: the ~184ms gap between two user turns elsewhere in the same session (segments of what may be one utterance split by server VAD). `silence_duration_ms` (500ms default) is already baked into each segment's recorded stop time, so the true acoustic gap was likely longer than 184ms, not shorter — genuinely ambiguous either way, and no currently-computed metric is distorted by keeping them as two turns. No measurement-integrity reason found to merge them, so left as-is.

**No tests, no migration, no commit-worthy code change** — this entry is documentation of a completed investigation, not a fix.

## Realtime timing metrics: the media/data-channel ordering race, part two, and a meaningful-overlap floor

The previous fix (below) still left one production control test — one deliberate, audible interruption — showing `confirmed_interruption_count = 0` and `overlap ≈ 0.5ms` across 2 events, with the underlying speaking-time/percentage metrics now physically plausible. The user's own hypothesis, verified against the actual architecture rather than assumed: WebRTC media (SRTP, carries the real audio) and the Realtime data channel (SCTP, carries `output_audio_buffer.started`) are two different transports multiplexed over one ICE/DTLS connection, with **no guaranteed relative ordering** — the same class of race `bargeIn.ts` already accounts for between `response.created` and audio reaching the speaker (see its own doc comment). Snapshotting `currentAiResponseId` at `speech_started` time (the previous fix) closes "state moved on by confirmation time," but not this narrower case: if the actual audio reaches the user's speakers moments *before* `output_audio_buffer.started` for that response has been processed on the data channel, the user can genuinely already be hearing the AI when they start talking, yet the snapshot still reads `null` at that exact instant.

**Audited the strongest available browser-side playback evidence, as instructed, before reaching for a workaround.** A real `<audio>` element does exist client-side (fed via `ontrack`), exposing genuine `playing`/`waiting`/`pause` events — these were the leading candidate for an authoritative "audio is rendering right now" signal. They are not usable here: OpenAI's output track is one continuous live `MediaStream` reused across every AI turn in the session, not a discrete clip per turn, so the element's playback-state transitions track *network/buffering health for the whole connection*, not per-turn silence between AI responses — they would not distinguish "response N's audio is playing" from "the pipe is merely idle between turns." Detecting genuine silence directly would require inspecting decoded audio sample energy (Web Audio API `AnalyserNode`), which is vocal/audio-level analysis and explicitly out of scope. No event that reliably marks "audio for response N is audible right now" exists on the client; none was invented.

**Fix: a small, explicitly bounded, documented reconciliation — not a second race, not a blanket rule.** `recordConfirmedBargeIn()` no longer resolves `context`/attribution/dedup immediately; it records the raw evidence only (the at-start snapshot, plus the triggering user turn's own `startMs`). Resolution now happens once, from scratch, inside `finalize()`, once the full timeline — including any `output_audio_buffer.started` that arrived shortly *after* speech began — is known: if a candidate interruption's AI state at speech-start was `"pre_playback"` (a response was pending, not yet marked playing), and that same response's `.started` is later found to have landed within `MEDIA_DATA_CHANNEL_SKEW_TOLERANCE_MS` (100ms) *after* the user's speech began, the two transports are treated as reporting the same real-world event a few ms apart, and the interruption is reclassified `"audible"`. 100ms was chosen deliberately far smaller than the 250ms–1.5s confirmation window itself, specifically so a response that only starts playing because real time genuinely passed (a true pre-playback case — "we do NOT want to classify all `response.created`→speech events as audible") cannot satisfy it; only two transports narrowly disagreeing about one already-real event can. The dedup set (`audibleInterruptedResponseIds`) is recomputed fresh on every `finalize()` call rather than mutated once persistently, so a duplicate `finalize()` stays idempotent — this was a real risk introduced by moving resolution later, caught and fixed during this same change.

**Overlap count 2 / duration ≈0.5ms, explained.** Re-inspected the raw interval endpoints: these were not a clock-domain bug (already ruled out in the previous round) but ordinary JS event-processing-order artifacts — two independently-timestamped `elapsed()` calls for two separate WebRTC data-channel messages landing a fraction of a millisecond apart purely because of dispatch order, not anything acoustically real. Added `MIN_MEANINGFUL_OVERLAP_MS = 10`, documented explicitly: real human speech overlap operates on the order of tens to hundreds of milliseconds at minimum; 10ms is comfortably below any perceptible unit of genuine simultaneous speech while comfortably above measurable event-loop jitter (typically sub-millisecond to low single-digit ms). An intersection below this floor is not constructed as an `OverlapIntervalMetric` at all — filtered at the source, not clamped or hidden after the fact. Once the interruption above is correctly reclassified, its real overlap (comfortably above 10ms, generally on the order of the confirmation window itself) is unaffected by this floor; only genuinely meaningless sub-10ms artifacts are excluded.

**No new migration** — the persisted shapes (`ConfirmedBargeInMetric`, `OverlapIntervalMetric`) are unchanged; only *when* and *how* `context`/`countsTowardInterruption`/overlap are computed changed, entirely inside `sessionTimeline.ts`.

**Tests added** (`tests/unit/sessionTimeline.test.ts`, 6 new): the exact production event ordering (speech starts, then `.started` for the same response lands a few ms later, within tolerance) reclassified `"audible"` with a meaningful overlap; a response starting 500ms later (outside tolerance) correctly staying `"pre_playback"`; a short-but-genuine reclassified overlap not accidentally filtered; a 1ms boundary artifact correctly filtered to zero overlaps; and the two "required result" scenarios verbatim (audible interruption → exactly one technical and one coaching-facing count with meaningful overlap; pre-playback-only session → zero coaching interruptions, zero overlap, no phantom AI turn).

## Realtime timing metrics: classify audible-vs-pre_playback at speech-start time, not confirmation time

With the AI-turn-lifecycle bug fixed (previous entry), production's next control test — one deliberate, audible interruption — still came back wrong: `confirmed_interruption_count = 0` and `overlap = 0.8ms` across 2 events, against `technical_barge_in_count = 5`.

**Audit, per the explicit instruction to reconstruct the raw timeline before touching any aggregate formula.** `recordConfirmedBargeIn()` computed both the audible/pre_playback `context` and which AI response to attribute the barge-in to by **reading `currentAiResponseId`/`pendingResponseId` live, at the moment the confirmation timer fires** — 250ms after `speech_started` by default, up to ~1.5s during the startup-guard window (see `startupGuard.ts`). That is not the same moment as when the candidate interruption interval actually began. Whether the AI was audibly speaking is a fact about the instant the user's speech started, not a fact to be re-derived later from shared mutable state that may have changed in the interim — the AI's turn can naturally conclude, get closed for an unrelated reason, or (across a reconnect) point at an entirely different response by the time confirmation fires, all without anything about the user's actual interruption having changed. Re-reading state at confirmation time silently misclassifies a genuine mid-playback interruption as `"pre_playback"` (or leaves it completely unattributed) purely because time passed between the two moments — exactly the mechanism the user's own hypothesis identified, and confirmed correct by tracing `bargeIn.ts` and `sessionTimeline.ts` together: `bargeIn.ts`'s own "AI finished naturally mid-timer → promote to immediate turn start" rule prevents a *fully* stale confirmation from firing in the simplest case, but nothing prevented `sessionTimeline`'s independently-tracked `currentAiResponseId`/`pendingResponseId` from having moved on by the time the (still-correctly-fired) confirmation callback ran and asked "is the AI speaking *right now*."

**Overlap/clock-domain audit — verified, no bug found there.** Re-read `UserTurnMetric.startMs`/`endMs` and `AiTurnMetric.startMs`/`endMs` end to end: both are unconditionally `elapsed()` (the client monotonic clock), for every turn, regardless of `durationSource`. The overlap and response-latency interval math (`Math.max`/`Math.min` over `startMs`/`endMs`) never touches the server's separate `audio_start_ms`/`audio_end_ms` clock, which is used *only* to compute a `server_vad`-timed user turn's own `durationMs` figure — a value that can legitimately differ from `endMs - startMs` for that one turn (by design, documented), but is never fed into overlap or latency. So the near-zero 0.8ms overlap was **not** a mixed-clock-domain bug — it was a downstream symptom of the same misclassification above: the confirmed-barge-in's own attribution can differ from the ai turn overlap ends up checked against, and a slim, coincidental boundary intersection between unrelated turns can surface as a tiny "overlap" while the real, substantial one goes unrepresented. A new regression test asserts this explicitly (deliberately mismatched server-clock values against the client clock, confirming overlap is computed entirely from the client-clock fields).

**Classifying the reported 5 technical barge-ins**: this environment has no live access to the production Supabase database, so the 5 specific rows cannot be enumerated here — after this fix ships and `0013` is applied, they (and any future session) are queryable directly: `select start_ms, barge_in_context, counts_toward_interruption, audible_ai_response_id_at_start, realtime_response_id from realtime_turn_events where session_id = '<id>' and kind = 'confirmed_barge_in' order by start_ms;`. What the fix guarantees going forward: a barge-in whose triggering user turn began while `output_audio_buffer.started` had already fired (and not yet closed) is `"audible"`; one that began during the `response.created`→`.started` gap is `"pre_playback"`; a repeat confirmation against an already-counted response is flagged `countsTowardInterruption: false`; and — per the separate reconnect fix below — a stale timer from an abandoned connection can no longer fire at all. The one deliberate interruption in the reported session should now show `context: "audible"`, `countsTowardInterruption: true`, and a plausible overlap duration once re-run.

**Fix** (`src/lib/realtime/sessionTimeline.ts`): `recordUserSpeechStarted()` now snapshots `currentAiResponseId` and `pendingResponseId` onto the user turn itself, at the instant speech starts (`audibleAiResponseIdAtStart`, `pendingAiResponseIdAtStart` — the former is also exposed on `UserTurnMetric` for diagnostics). `recordConfirmedBargeIn()` reads that snapshot (via whichever user turn is currently open) instead of re-deriving the answer from present-tense state; the AI turn marked `wasInterrupted` is likewise the one identified by the snapshot, so every derived signal — context, attribution, `wasInterrupted`, and (by construction, since it's the same turn's real `endMs`) overlap — agrees on the same moment-in-time answer. A defensive fallback to live state remains for the (should-never-happen) case where no open user turn is found, which is strictly no worse than the pre-fix behavior.

**A second, independent bug found during this audit and fixed alongside it**: `realtime-simulation-client.tsx`'s `connect()` creates a brand-new `bargeIn` controller on every call (initial connect and every reconnect) but never reset the *previous* one first. A real `setTimeout` does not get cancelled just because its enclosing JS closure is abandoned — if a reconnect happened while an old `bargeIn` instance's confirmation timer was still pending, that stale timer could fire later, invoking `onConfirmedBargeIn` against a dead connection and recording a spurious `recordConfirmedBargeIn()` metrics event uncorrelated with anything the user actually did (a legitimate instance of the "duplicate/stale event" category this audit was asked to check for). Fixed with a new `bargeInRef`, reset before creating each new controller and on unmount.

**Schema**: new additive migration `0013_audible_ai_response_id_at_start.sql` — `realtime_turn_events` gains `audible_ai_response_id_at_start` (`user_turn` rows only, external OpenAI response id, not a foreign key — matching `realtime_response_id`'s existing convention). No RLS/constraint changes, no existing data touched.

**Tests added** (`tests/unit/sessionTimeline.test.ts`, 5 new): a genuine mid-playback interruption correctly classified `"audible"` even when the AI turn closes (for an unrelated reason) before confirmation fires — the exact production event ordering; a true pre-playback case still correctly classified `"pre_playback"`; the at-start snapshot correctly recorded on `UserTurnMetric.audibleAiResponseIdAtStart`; a full end-to-end reproduction of the control-test scenario now producing both a counted interruption and a plausible (>250ms) overlap duration instead of near-zero; and an explicit clock-domain check proving overlap is computed entirely from client-clock fields even when server-clock values are deliberately set to a wildly different origin.

## Realtime timing metrics: AI turns staying open — the root cause behind 153% AI speaking time, 50s of spurious overlap, and a duplicated interruption count

Production's first real multi-turn session produced structurally impossible numbers: `total_ai_speaking_ms` (~156s) exceeding `total_duration_ms` (~102s), `ai_speaking_percentage = 153%`, 7 overlap events totaling ~50.5s, and `confirmed_interruption_count = 2` for a session where the user reported interrupting the AI exactly once. Per the explicit instruction to audit the raw timeline rather than patch the aggregates, the fix is entirely in the event-lifecycle representation — no value is clamped, capped, or rounded to fit a bound.

**Root cause (one bug, three symptoms).** `response.cancel` stops the server from generating further response content, but does **not** itself drain or stop the output audio buffer — per OpenAI's own docs, only an explicit `output_audio_buffer.clear` client event (or the server's own VAD-mode auto-interrupt, which requires `turn_detection.interrupt_response: true` — disabled here on purpose, see "Acoustic-echo false-interruption fix") actually does that. The component only ever sent `response.cancel` on a confirmed barge-in. So a genuinely interrupted AI turn's `output_audio_buffer.stopped` could arrive very late, or never — leaving that `AiTurnMetric` open (`endMs: null`) until `finalize()`, where it was closed using `finalizedAtMs`: the elapsed time at the very end of the whole session. One such turn, spanning from wherever it was interrupted to session end, explains all three symptoms:
1. **153% AI speaking time**: `totalAiSpeakingMs` sums every AI turn's duration; the phantom-open turn's duration alone could span most of the remaining session, and summed with the other genuinely-completed turns, comfortably exceeds `totalDurationMs`.
2. **7 overlaps / 50.5s**: the phantom-open interval overlaps with essentially every user turn that occurs for the rest of the session, each producing its own `OverlapIntervalMetric`.
3. **Response latency was not independently investigated — same cause**: the "preceding AI turn" search requires `a.endMs <= u.startMs` (no overlap). A phantom-open turn's inflated `endMs` almost never satisfies that for any user turn before session end, so it gets silently excluded from being "preceding" for anything — forcing the search to reach past it to a much older, genuinely-unrelated AI turn, and measuring latency against that instead. (This is exactly the reported ~23s median/average latency, and confirms the task's own suspicion: the latency bug was never a separate defect — it was a downstream consequence of the same open-turn bug, which is why it was not fixed independently.)

**Fix, two layers**:
1. **Primary**: `realtime-simulation-client.tsx`'s `onConfirmedBargeIn` now sends `output_audio_buffer.clear` immediately after `response.cancel` — the documented, correct two-step interrupt sequence. A new `case "output_audio_buffer.cleared":` mirrors `.stopped`'s handling exactly (clears `bargeIn`'s "AI speaking" flag, dispatches `AI_FINISHED_SPEAKING`, closes the `AiTurnMetric`).
2. **Safety net**: `sessionTimeline.ts`'s `recordResponseDone()` now closes any AI turn still open when the response concludes with a status other than `"completed"` (cancelled/failed/incomplete) — none of those statuses can produce further audio, so there's nothing left to wait for. A `"completed"` response is left to `.stopped`, since it may legitimately still be draining a few hundred ms of buffered audio. Both the primary fix and the safety net funnel through one shared, idempotent `closeAiTurn()` — whichever event arrives first wins; the other is a no-op.

**Interruption count became 2, not 1 — same root cause, plus an explicit idempotency fix.** With the AI turn staying open, `bargeIn`'s "AI speaking" flag also stayed `true` longer than it should have (it only clears on `.stopped`/`.cleared`/`response.done`), so a second raw `speech_started` — whether genuine continued speech with a natural micro-pause the server's VAD reported as two segments, an echo, or a stale/duplicate callback — could independently satisfy the 250ms confirmation window and fire `onConfirmedBargeIn()` a second time against the *same still-open* response. The primary fix closes that window quickly, which should prevent most recurrences on its own, but the task's own explicit requirement ("an audible interruption event must be idempotent per user-turn/AI-response pair") is now enforced directly and unconditionally, regardless of mechanism: `recordConfirmedBargeIn()` tracks which AI response ids have already produced a *counted* audible interruption; every confirmed barge-in is still recorded in full (`ConfirmedBargeInMetric`, `technicalBargeInCount` — unchanged, still a raw diagnostic total of every controller firing), but a repeat against an already-counted response is flagged `countsTowardInterruption: false` and excluded from `confirmedInterruptionCount`, the coaching-facing metric. This deliberately does **not** rely on transcript content to decide genuineness (echo can produce transcript text too) — the dedup key is the interrupted AI response itself, which is robust to whichever underlying mechanism produced the duplicate.

**New structural invariant check** (`validateSessionTimelineInvariants()` in `sessionTimeline.ts`, run at the end of every `finalize()`): flags, via `console.error` and a new `SessionTimelineSnapshot.invariantViolations: string[]` (included in the dev debug view, never persisted, never used to clamp anything), any of: `totalAiSpeakingMs > totalDurationMs`; `userSpeakingPercentage`/`aiSpeakingPercentage` outside `[0, 100]`; `totalOverlapMs` exceeding `min(totalUserSpeakingMs, totalAiSpeakingMs)`; any two AI turns' intervals overlapping each other; any two confirmed user turns' intervals overlapping each other. This product never plays multiple AI audio streams at once and a user cannot speak two turns simultaneously, so every one of these should always hold; a violation is meant to be loud and immediately actionable evidence of a future lifecycle bug, not something to silently paper over.

**Schema**: new additive migration `0012_ai_turn_lifecycle_and_idempotent_interruption.sql` — `realtime_turn_events` gains `counts_toward_interruption` (nullable, `confirmed_barge_in` rows only). The AI-turn-closing fix itself needed **no new column** — it only changes *when* the existing `end_ms`/`duration_ms` etc. get populated, not their shape.

**Tests added** (`tests/unit/sessionTimeline.test.ts`, 9 new): several sequential non-overlapping AI turns; an interrupted turn closing promptly via `.cleared` so a later response doesn't inherit its overlap; a late residual `.stopped` after `.cleared` treated as a no-op; stale/duplicate events (created/started/cleared/stopped/done all repeated) not double-counting; one real interruption reported as two raw VAD segments still counted exactly once; a false echo blip during a later AI turn never inflating the coaching count; AI speaking time bounded by session duration across a normal multi-turn conversation; overlap bounded by `min(user, AI speaking time)`; and response latency correctly paired with the immediately-preceding *audible* AI turn rather than a stale, unrelated earlier one.

## Realtime timing metrics: technical confirmed barge-in vs. audible user interruption

The attribution fix above (previous entry) surfaced a real product-semantics gap: a confirmed barge-in that lands in the `response.created` → `output_audio_buffer.started` gap is a genuine control-plane event (the barge-in controller cancelled a response), but the user never actually spoke over anything they could hear — there was no audio yet. Folding that into the same "confirmed interruption" count as a real, audible interruption would make the metric unusable as a coaching signal (it would count "the user started talking again slightly before the AI's reply had audibly begun" the same as "the user cut the AI off mid-sentence").

**Two concepts, now explicit:**
1. **Technical confirmed barge-in** — any `onConfirmedBargeIn` callback, i.e. any time the barge-in controller confirmed and cancelled a pending or active AI response. Every one is recorded, always, for debugging/session-control visibility.
2. **Audible user interruption** — a technical confirmed barge-in where AI audio was *actually playing* at the moment of confirmation. This, not the raw technical count, is the coaching-relevant metric.

**Implementation** (`src/lib/realtime/sessionTimeline.ts`): `ConfirmedBargeInMetric` gained `context: "audible" | "pre_playback"`, computed in `recordConfirmedBargeIn()` as `currentAiResponseId ? "audible" : "pre_playback"` — i.e. exactly the same signal already used to decide attribution (`currentAiResponseId` vs. the `pendingResponseId` fallback), just also captured as an explicit, queryable field rather than left implicit. `SessionLevelMetrics.confirmedInterruptionCount` (the existing, coaching-facing field — kept, not renamed, to avoid unnecessary churn) now counts `context: "audible"` entries only. A new `SessionLevelMetrics.technicalBargeInCount` holds the raw total (audible + pre_playback) for diagnostics. Overlap is untouched by this change — it was already, and remains, purely the intersection of a confirmed user-speech interval and an actual AI-playback interval, independent of barge-in context; a pre-playback cancellation correctly contributes zero overlap, same as before, now just correctly excluded from the coaching count too.

**Schema**: new additive migration `0011_barge_in_context.sql` — `realtime_turn_events` gains `barge_in_context` (nullable, checked `'audible'`/`'pre_playback'`, only ever set on `confirmed_barge_in` kind rows), `realtime_session_metrics` gains `technical_barge_in_count`. `confirmed_interruption_count`'s column comment is updated to state its (corrected) audible-only semantics explicitly. No table drop/recreate, no RLS/constraint changes, no existing data touched.

Still no phantom `AiTurnMetric` is fabricated for a response that never produced audio (unchanged from the previous fix) — a "turn" continues to mean a period of actual playback.

**Tests added** (`tests/unit/sessionTimeline.test.ts`): user starts during actual AI playback → audible interruption = 1; user starts after `response.created` but before playback → technical barge-in = 1, audible interruption = 0, no phantom AI turn; overlap stays 0 for the pre-playback case; and a mixed scenario (one pre-playback + one audible barge-in) confirming `technicalBargeInCount = 2`, `confirmedInterruptionCount = 1`, and that overlap is attributed only to the genuinely audible one — no double-counting in either direction.

## Realtime timing metrics: confirmed barge-in with zero overlap — attribution gap, not a calculation bug

Production reported a session with `confirmed_interruption_count = 1` but `overlap_count = 0` / `total_overlap_ms = 0`, despite the user intentionally interrupting the AI.

**Audit.** `sessionTimeline.ts` tracks two related but distinct notions of "the AI is currently talking":
- `bargeIn.ts` (governing whether a raw `speech_started` even starts a confirmation timer) treats the AI as "speaking" from **`response.created`** onward — deliberately, to close a real media/data-channel ordering race documented in `bargeIn.ts`'s own comment (audio can reach the speaker before the client has processed `output_audio_buffer.started`).
- `sessionTimeline.ts`'s own `AiTurnMetric` interval — the thing overlap and AI-speaking-time are computed against — only exists from **`output_audio_buffer.started`** to `.stopped`, i.e. actual audio playback, by design (this is deliberately narrower than "speaking," per the module's documented event-source audit: an `AiTurnMetric` is meant to represent what the user could actually *hear*).

Those two boundaries are not the same event, and the gap between them is real: `create_response: true` means the server auto-generates a reply as soon as the user's previous utterance ends, and there is always some model-generation latency between `response.created` and the first byte of audio (`output_audio_buffer.started`) — this gap is precisely what `avgAiResponseLatencyMs` measures. **If a confirmed barge-in lands inside this gap** — the user starts talking again quickly enough that `bargeIn.ts` (which already considers the AI "speaking") confirms an interruption before the response ever produces any audio — then `sessionTimeline.ts` had no `AiTurnMetric` for that response at all (`recordAiAudioStarted` is never called for a response cancelled before playback begins). `recordConfirmedBargeIn()` fell back to `aiResponseId: null` in that case, and no AI turn was flagged interrupted.

**Zero overlap in this specific case is factually correct — there was no audio to overlap with.** This is not a calculation bug; it's the conceptual distinction the product deliberately preserves (a confirmed interruption does not mechanically imply one overlap event — see the module's own doc comment). The real bug was the **attribution**: the confirmation was recorded with `aiResponseId: null` instead of naming the response it actually pre-empted, making the row look orphaned/inconsistent rather than a legitimate, fully-explained zero-overlap outcome.

(For the *other* case — a barge-in confirmed while AI audio is genuinely already playing — the existing code was already correct: `currentAiResponseId` is set from `output_audio_buffer.started` and only cleared by `.stopped`, so `recordConfirmedBargeIn()` already attributes correctly and the AI turn's `endMs`, set later by `.stopped`, is always after the user's turn start, always yielding positive overlap. Confirmed by the new regression test for that path — see below.)

**Fix**: `sessionTimeline.ts` gained `recordResponseCreated(responseId)`, wired to `response.created` in `realtime-simulation-client.tsx` (alongside the existing `bargeIn.handleAiSpeakingChanged(true)` call there). It tracks a `pendingResponseId` — a response that has been created but hasn't started producing audio yet — cleared the moment that response either starts playing (`recordAiAudioStarted`) or concludes without ever doing so (`recordResponseDone`). `recordConfirmedBargeIn()` now attributes to `currentAiResponseId ?? pendingResponseId`, so a barge-in confirmed in the gap correctly names the response it interrupted. Deliberately **no phantom `AiTurnMetric` is created** for a response that never produced audio — a "turn" in this module specifically means a period of actual playback; fabricating a zero-duration entry would misrepresent AI speaking time and inflate `aiTurnCount` for something nobody ever heard. Overlap, `aiTurnCount`, and `avgAiTurnDurationMs` are therefore unaffected by this fix — only the `confirmedBargeIns[].aiResponseId` attribution changed.

**Tests added** (`tests/unit/sessionTimeline.test.ts`): the normal case (user begins speaking during active AI playback, barge-in confirms at 250ms, AI is cancelled, overlap reflects the real simultaneous-speech interval — not the whole user turn — and neither the interruption count nor the overlap count/duration is double-counted); the gap case (confirmed barge-in between `response.created` and `output_audio_buffer.started` — attributed to the pending response, zero overlap confirmed correct, no phantom AI turn created); and a check that a since-cleared pending response id is never resurfaced for a later, unrelated confirmed barge-in.

## Realtime timing metrics, numeric type fix: `integer` columns can't hold monotonic-clock milliseconds

Production (Vercel) reported every `/api/simulation/realtime/metrics` call failing with Postgres error `22P02`: `invalid input syntax for type integer: "16258.5"`. Both `realtime_turn_events` and `realtime_session_metrics` remained permanently empty — `saveRealtimeTurnEvents` (called first, inserting turn events) threw on the very first insert, so `upsertRealtimeSessionMetrics` was never even reached; that single failure point explains why *both* tables were empty, not just one.

**Root cause**: `sessionTimeline.ts`'s durations are derived from `performance.now()`, a monotonic clock with sub-millisecond resolution — every `start_ms`/`end_ms`/`duration_ms` value, and everything arithmetically derived from them (sums, averages, medians, overlap intersections, response latencies), is inherently fractional. Migration `0009` declared these columns `integer`. The application data was correct; the column types were wrong.

**Postgres can't name the column for this error class.** `22P02` reports the offending *value* ("16258.5") but never the column — unlike a NOT NULL or CHECK violation. So the exact column that first triggered the error in production can't be identified from the error message alone; any of the five `realtime_turn_events` ms columns, or the twelve affected `realtime_session_metrics` columns below, could produce this exact symptom depending on which turn/metric happened to be inserted/upserted first. Going forward, `src/lib/db/realtimeMetrics.ts` now logs the full row payload (numbers/booleans/enums only — this table holds no transcript text) alongside `code`/`details`/`hint` on any insert/upsert failure, so a future mismatch is diagnosable directly from logs instead of by guesswork.

**Audit — every column whose type was wrong**:
- `realtime_turn_events`: `start_ms`, `end_ms`, `duration_ms` (all client-monotonic-clock-derived, or a subtraction of server VAD ms — see below), `server_audio_start_ms`, `server_audio_end_ms`.
- `realtime_session_metrics`: `total_duration_ms`, `total_user_speaking_ms`, `total_ai_speaking_ms`, `total_overlap_ms`, `avg_user_turn_duration_ms`, `longest_user_turn_ms`, `avg_ai_turn_duration_ms`, `avg_user_response_latency_ms`, `median_user_response_latency_ms`, `longest_user_response_latency_ms`, `avg_ai_response_latency_ms`, `median_ai_response_latency_ms`.

`server_audio_start_ms`/`server_audio_end_ms` (OpenAI's `audio_start_ms`/`audio_end_ms`) were converted too, proactively: the SDK types them as plain `number` with no documented integer guarantee, and a millisecond offset derived from an audio sample count can in principle be fractional depending on sample rate — the same class of risk as the client-clock fields, so they weren't assumed safe just because production hasn't (yet) shown a fractional value there.

**What stayed `integer`, and why**: `turn_index` (always a whole array position), `user_turn_count`, `ai_turn_count`, `overlap_count`, `confirmed_interruption_count`, `suspected_noise_event_count` (all genuine counts — `.length` or increments, never fractional by construction). `user_speaking_percentage`/`ai_speaking_percentage` were already `numeric(5,2)` in `0009`, not `integer` — no bug there, untouched. The fix is a type correction, not a blanket conversion: `.int()` stays exactly where zod already had it (turn indices, counts), and no field's real precision was rounded away in application code to force it to fit a column — the column was made to fit the data instead.

**Migration**: since `0009` is already applied to production, `supabase/migrations/0010_fix_realtime_metric_numeric_types.sql` (new, additive) uses `ALTER TABLE ... ALTER COLUMN ... TYPE double precision USING ... ::double precision` for each column above, restates the three `not null default 0` defaults explicitly after the type change, and touches nothing else — no table drop/recreate, no RLS/constraint changes, no `conversation_messages`/`evaluations` data. Both tables are confirmed empty in production (every prior insert attempt failed), so there's no existing data to convert, but the `USING` clauses are written to be safe regardless.

**Refactor for testability**: the validation schema and DB-row mapping (previously inline in the route handler) moved to `src/lib/realtime/metricsPayload.ts` (`metricsPayloadSchema`, `mapMetricsPayloadToTurnEvents`, `mapMetricsPayloadToSessionMetrics`), mirroring the existing `src/lib/coaching/schema.ts` pattern, so the exact production value (`16258.5`) and other fractional cases are directly unit-testable without a live database. The route handler is now a thin orchestrator. No zod schema actually changed — none of the affected fields were ever declared `.int()`, so validation already accepted fractional input; the bug was purely at the database column level.

**Persistence atomicity — verified, not changed**: `saveRealtimeTurnEvents` and `upsertRealtimeSessionMetrics` are two independent Supabase calls, each its own implicit transaction — not wrapped in one atomic operation. That's exactly why this bug emptied both tables: the turn-events insert (called first) threw immediately, so the session-metrics upsert was never attempted. With the type fix, this specific failure mode is closed, but the lack of cross-table atomicity remains: a *future* failure isolated to the session-metrics upsert (after turn events already inserted) would leave partial data for that session until the next successful finalization overwrites it (both paths are idempotent — delete-then-reinsert / upsert-by-`session_id` — so a retry self-heals). This was judged acceptable to leave as-is rather than wrapping both calls in a Postgres function/transaction, since it's outside the scope of this fix and the existing idempotent design already bounds the damage to "stale until the next retry," never data corruption. The governing requirement — a metrics-persistence failure of any kind must never affect the transcript or evaluation — is untouched and re-verified: both calls remain wrapped in `finishAndEvaluate`'s own try/catch, entirely before and independent of the `/api/practice/end` call.

**Action required in production**: run `supabase db push` (or apply `0010_fix_realtime_metric_numeric_types.sql` directly) against the production Supabase project.

## Realtime timing metrics, measurement-integrity fix: a raw VAD blip is not a user turn

Caught before migration `0009` was ever applied to production: the first version of `sessionTimeline.ts` treated every raw `speech_started` → `speech_stopped` pair as a real user turn, full stop. Since production testing had already confirmed false `speech_started` events from speaker echo (see "Acoustic-echo false-interruption fix" below), this meant a rejected VAD blip — never confirmed as a real barge-in — would still silently count toward `userTurnCount`, `totalUserSpeakingMs`, `avgUserTurnDurationMs`/`longestUserTurnMs`, both response-latency calculations, and overlap. A genuine measurement-integrity bug, confirmed by re-reading the code rather than assumed.

**Classification, not deletion.** A raw `speech_started`/`speech_stopped` pair alone is not evidence of a real user turn — but a short duration alone isn't evidence of *noise* either ("yes", "no", "why?" are real, valid turns). `sessionTimeline.ts` now classifies every user speech event as `"confirmed"` or `"suspected_noise"` using, in priority order:
1. **It triggered a confirmed barge-in** (the existing `bargeIn.ts` controller's `onConfirmedBargeIn`) → always `"confirmed"`, regardless of transcript or duration. A confirmed barge-in can only fire while the triggering user turn is still open (a blip that stops before confirmation never reaches that callback — see `bargeIn.ts`), so `recordConfirmedBargeIn()` attributes itself to whichever user turn is currently open. This is a purely retrospective metrics decision — it does **not** gate or delay live barge-in behavior, which continues to work exactly as before.
2. **It has a non-empty transcript** → `"confirmed"`. Meaningful transcript text is direct evidence of real speech regardless of brevity — this is what protects genuine short replies from being discarded.
3. **Transcription explicitly failed, or explicitly completed with empty text** → `"suspected_noise"`. The server's own transcriber concluding there was nothing to transcribe is strong negative evidence, independent of duration. (New: `recordUserTranscriptionFailed()`, wired to the existing `conversation.item.input_audio_transcription.failed` event, which previously only produced a debug log.)
4. **Otherwise** (transcription never arrived by finalize time — still pending, or lost) → fall back to duration (`AMBIGUOUS_NO_TRANSCRIPT_MIN_MS = 300`ms). OpenAI's default `silence_duration_ms` (500ms, left at the SDK default) means the server already waits ~500ms of trailing silence before emitting `speech_stopped`, so genuine turns are rarely this short — but this path still errs toward keeping anything but the briefest events, since duration alone can't establish certainty either way.

This does not require completed transcription before allowing a live interruption — the component already waits for pending transcription (`waitForPendingUserTranscription`) before calling `finalize()`, so classification evidence is available for essentially every turn by the time it runs; a still-pending case simply falls through to rule 4.

**What changed in the data**: `UserTurnMetric` gained `classification` and `transcriptionFailed`; `turnIndex` is now `number | null` — assigned only to confirmed turns, in chronological order, since a suspected_noise event isn't part of the numbered conversation. Every session-level aggregate (`userTurnCount`, speaking time, avg/longest duration, both response latencies, overlap) is now computed from confirmed turns only; a suspected_noise event is still returned in the full `userTurns` list for diagnostics, just excluded from every derived number. A new `suspectedNoiseEventCount` on `SessionLevelMetrics` gives at-a-glance visibility into how many events were excluded, without needing to query raw turn events.

**Schema**: since migration `0009_realtime_timing_metrics.sql` had not yet been applied to production, it was edited in place rather than superseded by a new migration — `realtime_turn_events` gained `user_turn_classification` and `transcription_failed` columns (both null for non-`user_turn` kinds), and `realtime_session_metrics` gained `suspected_noise_event_count`. **Action required**: run `supabase db push` against the corrected migration — the same single step as before, just with the corrected file content; there is no separately-applied intermediate version to reconcile.

No vocal analytics, methodology, or scoring work was touched — this is strictly a correction to the measurement layer's own internal accuracy.

## Realtime timing metrics: an objective measurement layer, not yet a coaching signal

With Realtime conversation stabilized (speech-to-speech, echo/startup false-interruption fixes, genuine barge-in, graceful timer completion), the next phase is a **measurement layer only**: capture objective conversational timing/interruption facts, store them, and stop — no emotional/vocal analysis, no change to Evaluation Engine scoring, no production UI.

**Event-source audit** (`src/lib/realtime/sessionTimeline.ts`), verified directly against `node_modules/openai/resources/realtime/realtime.d.ts` rather than assumed:
- User turn boundaries: `input_audio_buffer.speech_started`/`.speech_stopped`. Both carry a server-authoritative `audio_start_ms`/`audio_end_ms` (ms since the input buffer began receiving audio for the session) plus a shared `item_id` — the most precise, duplicate-safe signal available, so **user turn duration prefers `audio_end_ms − audio_start_ms`** over any client-derived timing, falling back to the client clock only when the server fields are absent.
- AI turn boundaries: `output_audio_buffer.started`/`.stopped` (WebRTC/SIP-only, documented as bracketing actual output-audio streaming to the client) — closer to "what the user actually hears" than `response.created`/`response.done`, which reflect generation, not playback. Neither carries a timestamp, only `response_id`, so **AI turn timing is necessarily client-receipt-based**.
- AI turn text: `response.output_audio_transcript.done`. AI turn outcome: `response.done`'s `response.status` (`completed`/`cancelled`/`failed`/`incomplete`) — the server's own record of whether a turn was cut short.
- Confirmed user interruption: the *existing* barge-in controller's `onConfirmedBargeIn` callback — deliberately **not** every raw `speech_started`, since false VAD/echo events are already known to occur (see the two "false interruptions" entries below) and must never be counted as interruptions here either.

**Clock design**: a single injectable monotonic clock (`performance.now()` in production, a manual counter in tests) is used for every cross-boundary duration — user turn duration (client-fallback path), AI turn duration, overlap, and both response-latency metrics all share this one clock. The server's `audio_start_ms`/`audio_end_ms` is used *only* to compute a user turn's own duration (start and end come from the same server clock), never mixed into cross-turn math (overlap, latency) against the client clock, since there's no established offset between the two clocks — documented in code rather than inventing an unverified calibration.

**Overlap vs. confirmed interruption — deliberately distinct signals**: overlap is the objective intersection of a user speech interval and an AI playback interval (`Math.max(starts)` to `Math.min(ends)`, computed pairwise over every closed turn at `finalize()`); confirmed interruption is only ever incremented by the existing barge-in controller's confirmation. A user turn can overlap an AI turn without a confirmed barge-in ever firing (the confirmation window can still be running when the AI naturally finishes), and a confirmed barge-in always implies overlap but is counted separately. Both are persisted; neither is relabeled as the other.

**Response latency**: `avgUserResponseLatencyMs` = user speech start − the immediately preceding AI turn's end, but **only** over AI turns that ended strictly before that user turn started (no overlap) — an overlapping pair is a barge-in/overlap, not latency, and is simply excluded from the average rather than counted as zero or negative. `avgAiResponseLatencyMs` is the symmetric calculation and is explicitly documented (in the type, the migration, and here) as a **system/product-quality metric only** — it must never be surfaced as, or folded into, a user communication-performance score.

**Accuracy safeguards**, all in `sessionTimeline.ts` itself so every caller gets them for free: duplicate `recordUserSpeechStarted`/`recordAiAudioStarted` for an already-open turn is a no-op (guards Realtime event replay on reconnect); a turn still open at `finalize()` (manual End Practice doesn't wait for the in-flight exchange) is closed at the finalize instant and flagged `endedBySessionClose: true` — kept **strictly separate** from `wasInterrupted` (only ever set by a confirmed barge-in or a `cancelled` response status), so an abrupt manual stop is never misreported as the AI having been interrupted by the user; `finalize()` is safe to call more than once (returns a snapshot from the same closed state rather than mutating it further), giving idempotent finalization without any separate "already finalized" flag.

**Schema** (`supabase/migrations/0009_realtime_timing_metrics.sql`, additive, does not touch `practice_sessions`/`conversation_messages`/`evaluations`/old migrations): one kind-discriminated `realtime_turn_events` table (`kind in ('user_turn','ai_turn','overlap','confirmed_barge_in')`) holding per-event timestamps/durations/flags as real columns (not JSON — only a small `metadata jsonb` for genuinely unstructured extras), plus one `realtime_session_metrics` row per session (unique `session_id`) with the derived aggregates. RLS follows the existing owner-via-`practice_sessions` pattern; `realtime_turn_events` also gets a `delete` policy and `realtime_session_metrics` an `update` policy, both specifically so finalization's delete-then-reinsert / upsert-by-`session_id` persistence stays idempotent under a retry.

**Privacy**: no raw audio, ever — not mic buffers, blobs, data URIs, or waveform samples. Persisted fields are limited to timestamps (ms since session start), durations, booleans/enums, and transcript text (already persisted elsewhere as `conversation_messages`). Asserted in `tests/unit/sessionTimeline.test.ts`'s dedicated test via a serialized-snapshot key allow-list.

**Wiring** (`src/components/practice/realtime-simulation-client.tsx`): `metricsRef` (a `SessionTimeline`) is created once at mount and spans the whole practice session across any WebRTC reconnect — deliberately different from `bargeIn`'s per-connection controller, since a reconnect is a technical hiccup for the metrics layer, not a new session. `finishAndEvaluate` calls `finalize()`, logs `formatSessionTimelineDebugLines()` via `console.debug` (item 10's dev/QA view — no production UI yet), and best-effort `POST`s the snapshot to `/api/simulation/realtime/metrics`, all inside its own `try/catch` **before** the transcript flush and `/api/practice/end` call — a metrics failure is logged and swallowed, never allowed to cost the user their transcript or evaluation.

**Not done, deliberately**: no use of these metrics in Evaluation Engine scoring or prompts (`VOCAL_EVIDENCE_AVAILABLE` stays `false`); no production-facing UI; no vocal/pitch/emotion analysis; no Admin Panel/User Profile/payments work. This is a measurement layer, stopping point as specified.

## Startup false interruptions, round 2: a grace period anchored to actual AI audio, not a flat window

A screen recording of the next production test reproduced the false interruption again, with a concrete timeline: AI visibly speaking ~1.5–2.0s; UI falsely switches to Listening ~2.5s (user silent); Thinking ~3.5s; AI resumes ~4.0s; ~1.5s gap in the recorded audio between the two AI speech segments. Since "Listening" only appears once `onConfirmedBargeIn` fires — i.e. after the full confirmation window has elapsed — a switch at 2.5s with the round-1 fix's flat 500ms window means the false `speech_started` began at or within a few hundred ms of when AI audio itself started (~1.5–2.0s) and **persisted well past 500ms**. That's direct confirmation of what round 1 could only infer: the round-1 fix (a flat, wider 500ms confirmation for the whole first turn) was not conservative enough for the very start of that turn specifically, where the browser's echo-cancellation filter has had the least time to adapt.

**Why not just raise the flat window further** (e.g. to 1500ms for the whole first turn): a flat window protects the *whole* first turn equally, but the actual risk is concentrated in the first ~1 second after AI audio begins, not spread evenly across the whole opening line — a flat 1500ms would needlessly slow down a genuine interruption anywhere in the first turn, not just its start.

**Fix**: `src/lib/realtime/startupGuard.ts` (new) — `computeStartupConfirmMs(elapsedSinceFirstAiAudioMs)` returns `max(0, STARTUP_GRACE_MS − elapsed) + STARTUP_FOLLOWUP_CONFIRM_MS`, with `STARTUP_GRACE_MS = 1000` and `STARTUP_FOLLOWUP_CONFIRM_MS = 500`. This is a *continuous* formula anchored to when AI audio actually started playing (never before — there is nothing for echo cancellation to adapt against before playback begins, so a pre-playback delay was again ruled out), not a hard "in grace / out of grace" branch: speech starting the instant audio begins requires the full 1500ms to confirm; speech starting 900ms in requires only 600ms more; once 1000ms has fully elapsed since audio started, it collapses to exactly the same 500ms follow-up window round 1 already used for the rest of the first turn. `elapsed = null` (the `speech_started`/`output_audio_buffer.started` ordering race from round 1 — see the entry below) is treated as elapsed-0, the most conservative case. `bargeIn.ts`'s `confirmMs` function is called again from the component, now via `computeStartupConfirmMs`, so the mechanism plugged straight into the existing round-1 architecture without changing `bargeIn.ts` itself. Diagnostic logging (`confirmMsUsed` in `speech_started_during_ai_audio`) now reflects the actual dynamic value computed for each incident, so the next test can directly verify what was required versus what was observed.

Worst case for a genuine interrupter speaking right at the very start of the opening line: ~1.5s to confirm, once, for that one turn only — accepted per the task's explicit tradeoff ("even if interruption is slightly slower during this one startup window"). Every later turn is unaffected (flat 250ms, unchanged); VAD threshold unchanged (still 0.6); no muting.

## Startup-specific false interruptions: a state race plus AEC convergence, not a general VAD problem

After the echo/VAD fix (previous entry), production got much better but still saw several false interruptions clustered at the very start of the conversation over speakers, none over headphones, and none later in the same session once things had "settled." That pattern — startup-only, not conversation-wide — rules out the VAD threshold as the cause (a genuinely too-sensitive threshold would misfire throughout, not just at the start), so it was **not** raised again; it's still 0.6.

**Root cause, two compounding factors, both genuinely startup-specific:**

1. **A real state race** (`src/lib/realtime/bargeIn.ts`, `src/components/practice/realtime-simulation-client.tsx`): the barge-in controller's "is the AI speaking" flag was previously only ever set by `output_audio_buffer.started`/`.stopped`. Media (SRTP) and Realtime data-channel events are two different transports with no ordering guarantee between them — it's entirely possible for the AI's audio to reach the speaker fractionally before the `output_audio_buffer.started` event has been received and processed by the client. During that gap, the controller still believes the AI *isn't* speaking, so a `speech_started` arriving in it is treated as ordinary immediate turn-taking with **zero confirmation delay** — the one case explicitly designed to skip the protection, because normally there's nothing playing yet for it to protect against. That gap exists on every AI turn in principle, but it's the *opening line specifically* where it's most likely to actually matter (see factor 2), so this reads as a startup bug even though the underlying gap is general.
   - **Fix**: also treat `response.created` — the very first event of response creation, which OpenAI's docs confirm always precedes any audio — as "AI is speaking now." This closes the gap: by the time any audio could possibly reach the speaker, the controller already has the confirmation window active. `response.done` — "always emitted, no matter the final state" — was added as the matching backstop to clear the flag, so it can never get stuck `true` for a response that ends without ever actually producing audio (e.g. cancelled before playback starts).
2. **Acoustic echo cancellation (AEC) convergence lag**: browser echo cancellation is an adaptive filter that needs a live reference of the *output* signal to learn what to cancel from the *input* — it has nothing to adapt against until playback actually starts, so the first second or so of the very first AI turn is measurably the point where the AEC filter is least converged and echo leakage into the mic is most likely to cross the VAD threshold. This is a well-known characteristic of AEC, not a bug, and it inherently cannot be fixed by acquiring the microphone earlier or delaying `getUserMedia` — there is nothing to converge against before output begins, so a pre-playback "mic warm-up" delay was evaluated and rejected: it would add a delay to every single conversation for no benefit (the adaptation clock only starts once the AI's opening line begins playing, so a warm-up before that point achieves nothing) while not touching the one turn that's actually at risk.
   - **Fix, narrowly scoped**: `STARTUP_BARGE_IN_CONFIRM_MS = 500` (double the normal 250ms) applies *only* to the AI's first turn — set via `bargeIn.ts`'s `confirmMs` option now accepting a function, resolved fresh on every `speech_started` rather than fixed at construction, so the same controller instance can use the wider window for the opening line and silently revert to the normal 250ms the moment that turn's audio finishes (`isFirstAiResponseRef`, flipped in the existing `output_audio_buffer.stopped` handler, reset again on a genuine reconnect since that restarts the whole audio pipeline). No change to the VAD threshold, no muting, no delay added anywhere outside this one turn — a real, sustained interruption of the opening line still works, just via a still-fast (half-second) rather than the usual quarter-second confirmation.

**Diagnostics added** to actually verify this in the next production test rather than relying on inference: `speech_started`/`speech_started_during_ai_audio` debug logs now carry `isFirstAiResponse`, `confirmMsUsed`, `sessionElapsedMs`, `sinceFirstAiAudioMs` (time since `output_audio_buffer.started` first fired), and — only for the first-turn case, to avoid bloating every later turn's logs — the actually-applied `track.getSettings()` mic settings. New `ai_response_created`/`ai_response_done` debug events make the response lifecycle's timing directly visible.

No global VAD threshold change (still 0.6), no muting, no raw audio storage, no vocal/timing analytics.

## Evidence-integrity recovery, round 3: sanitize the field, don't reject the whole evaluation

Production confirmed the round-2 code-level validator was correctly *catching* violations, but its recovery strategy was too destructive: `dimensions.non_escalation.explanation` contained "tone," the one regenerate attempt still contained "tone," and the whole evaluation was rejected — `/api/practice/end` returned 502 and a user who had completed a real session lost their entire feedback report over one leftover word in one field. The detection logic itself was not weakened at all; only what happens after a violation survives regeneration changed.

**New recovery order in `runEvaluation`** (`src/lib/coaching/evaluationEngine.ts`):
1. Generate normally; validate schema (unchanged: one retry, then a genuine throw — this path is untouched, since a schema failure is a different, real problem).
2. Scan **every** text field for a paralinguistic claim (`findAllParalinguisticViolations`, new — the old `findParalinguisticViolation` returned only the first match, which was enough to trigger a retry but not enough to know what still needs fixing afterward).
3. If any exist, regenerate the whole evaluation once, same as before.
4. If the regenerated result *still* has violations (or itself fails schema validation, in which case the original — still schema-valid — result is used instead of discarding everything), **sanitize only the offending field(s)** rather than throwing.
5. Re-validate the sanitized object against the zod schema as a final safety net (should always pass, since sanitization only ever replaces a string within its own length limit) — a genuine last-resort throw stays reachable in principle, but only if sanitization itself somehow produced invalid output, never merely because a paralinguistic word was present.

**The sanitizer** (`src/lib/coaching/evidenceIntegrity.ts`, `sanitizeEvaluationOutput` + `sanitizeParalinguisticText`), per field:
- Try an ordered set of meaning-preserving phrase rewrites first — most specific idiom first, generic word-level fallback last, each rule operating on the previous rule's output: `"respectful tone"` → `"respectful wording"`, `"calm tone"`/`"calm demeanor"` → `"non-escalatory language"`, `"didn't raise their voice"` → `"did not use hostile or escalating language"`, `"sounded confident"` → `"stated their position directly"`, and generic `"<adjective> tone"` → `"<adjective> wording"`, bare `tone`/`voice`/`demeanor`/`volume`/`pace` → `wording`, `calm(ly/ness)` → `non-escalatory`, `vocal` → `verbal`.
- Re-check the rewritten text against the same violation patterns. If it's clean and still fits the field's schema length limit, use it — the original coaching point is preserved, just reworded onto transcript-safe ground.
- If no safe rewrite exists (e.g. "hesitation," "emotional state," or an unrecognized "sounded X" — concepts with no clean transcript-based equivalent, where a naive word swap risks inverting the meaning) or the rewrite doesn't fit the length limit, that one field — and only that field — is replaced with a short, generic, always-valid, transcript-grounded statement (e.g. "This reflects the wording used, not any assumed delivery."). Every other field, including the rest of the same dimension, is untouched.
- Every sanitized field is logged (`concept`, `method: "phrase_rewrite" | "neutral_fallback"`) alongside the original violation log, so production visibility into what's being caught and how it's being fixed is unchanged.

No rubric, scoring, methodology, or feedback-layout change — this only changes what happens to the *wording* of one field when the model still gets it wrong after one retry. No vocal analytics were added.

## Acoustic echo causing false Realtime interruptions: client-controlled barge-in confirmation

Production symptom without headphones: the AI's speech would suddenly stop and the UI would flip to Listening with no one having spoken; the same conversation over headphones never false-triggered even once. That contrast is the smoking gun for acoustic echo — the AI's own speaker output leaking into the microphone and registering as a `speech_started` VAD event.

**Audit findings (before any change)**:
- `getUserMedia({ audio: true })` — no constraints requested at all; browser default echo-cancellation behavior was never verified or logged.
- `turn_detection: { type: "server_vad", create_response: true, interrupt_response: true }` — no `threshold`, `prefix_padding_ms`, or `silence_duration_ms` set, so the SDK defaults applied: `threshold` 0.5, `prefix_padding_ms` 300ms, `silence_duration_ms` 500ms.
- **Why this is fragile by construction, not just under-tuned**: the SDK's own doc comment on `interrupt_response` states it cancels the active response "when a VAD **start** event occurs" — server-side, unconditionally, the instant a single `speech_started` arrives. There is no server-exposed "wait and confirm" option. So even perfect echo cancellation and a much higher threshold would only reduce the *frequency* of false starts, never eliminate the fact that any one brief blip (a click, a breath, real echo) instantly and irreversibly cancels the AI's speech with zero client involvement. Option A alone (browser processing + threshold) could not fully satisfy "a tiny echo, click, breath, or brief false VAD activation must not immediately cut off the AI" — Option B (client-controlled interruption) was necessary regardless of how good Option A is.

**Fix, both layers together**:
1. **Browser mic processing** (`src/lib/realtime/webrtcClient.ts`): `getUserMedia` now requests `{ echoCancellation: true, noiseSuppression: true, autoGainControl: true }` — as plain (non-`exact`) constraints, which the WebRTC spec treats as best-effort "ideal" values a browser can silently ignore rather than throwing `OverconstrainedError` if unsupported, so this degrades gracefully everywhere. The actually-applied settings are read back via `track.getSettings()` and surfaced through a new optional `onMicTrackSettings` handler for debug logging — never assumed, and never containing audio itself.
2. **VAD threshold, old vs new**: `threshold` raised from the SDK default **0.5 → 0.6** — a moderate increase (not toggled to an extreme like 0.9), reasoned as: leaked speaker echo reaching the mic is acoustically quieter than a person speaking directly into it, so a threshold that requires moderately louder input should suppress most echo/ambient-noise blips while still easily catching deliberate speech. `silence_duration_ms` (500ms) and `prefix_padding_ms` (300ms) were deliberately left at their defaults — they govern when speech is judged to have *ended*, not whether it should count as *started*, and the task was explicit that changing end-of-speech timing does not address a false-start problem.
3. **Client-controlled barge-in confirmation** (`src/lib/realtime/bargeIn.ts`), the primary fix: `interrupt_response` changed **`true` → `false`**. The server no longer auto-cancels on any VAD start event; `create_response` stays `true` so replies are still generated automatically once a real turn ends. A new `createBargeInController` now makes the interrupt decision instead: when `speech_started` arrives while the AI is *not* speaking, it's reported immediately (ordinary turn-taking, no echo risk since nothing is playing to leak back). When it arrives *while the AI is speaking*, the controller waits a short, fixed confirmation window (`DEFAULT_BARGE_IN_CONFIRM_MS = 250`ms) before doing anything: if `speech_stopped` arrives first, it was a blip — nothing was ever touched, the AI keeps talking uninterrupted. If speech is still ongoing once the window elapses, that's treated as genuine barge-in: the client explicitly sends `response.cancel` and the UI switches to listening, at which point the conversation proceeds exactly as it did before this change. If the AI's response finishes naturally while a confirmation is still pending, the controller promotes it straight to an ordinary turn-start rather than leaving anything waiting. 250ms was chosen as clearly perceptible-as-instant for genuine speech (a real utterance is essentially never that short) while still meaningfully longer than a click, breath, or echo tail.
4. **Diagnostics** (`src/lib/realtime/debugLog.ts`): every relevant Realtime event (AI audio started/completed, speech started/stopped, response cancellation, transcription completed/failed) is now logged via `console.debug`, plus one composite `speech_started_during_ai_audio` event carrying duration-until-stopped and whether it was actually interrupted — enough to distinguish real barge-in, echo, a short blip, and a genuine utterance from the browser console alone, without ever logging audio or transcript content.

**Explicitly not done here** (per the task's scope): no raw audio persistence, no timing/vocal-delivery metrics or scoring, no changes to the practice UI or feedback methodology, no Phase 3 analytics.

## Evidence integrity, round 2: a code-level guardrail, because the prompt alone isn't reliable enough

Production produced "The user maintained a respectful tone…" / "Maintained a respectful tone throughout the conversation." *after* the round-1 rubric-data fix and prompt guardrail (previous entry below) had already shipped.

**Exact remaining source, found by direct audit** — not a rubric-data problem this time. `git show 21cdaaf:supabase/seed.sql` (the original, pre-fix seed) and the current `supabase/seed.sql` were both grepped for `respect`/`tone`: neither ever contained the phrase "respectful tone," in any tool's `evaluation_criteria`, `coaching_guidance`, `core_principles`, `common_mistakes`, or `step_by_step_method`, before or after round 1. So this claim was never sourced from rubric text — it's the model's own default vocabulary for praising good communication, independent of what the rubric says. The actual gap: the round-1 guardrail's list of forbidden example sentences ("maintained a calm demeanor," "didn't raise their voice," "sounded frustrated," "spoke hesitantly") was made up entirely of *negative/critical*-sounding vocal claims. The model apparently generalized the prohibition to *complaints* about vocal delivery, not to *compliments* phrased the same way — "respectful tone" is flattering, so it slipped through. Whether migration `0008` has actually been applied to the production database is a separate, still-open question (this session has no credentials to the production Supabase project to check directly), but it's not the explanation for *this specific* claim either way, since the claim was never rubric-sourced.

**Fix, now with a real enforcement layer instead of relying on the prompt alone**:
1. **Prompt**: the guardrail now says explicitly "this applies equally to praise and to criticism, so a flattering vocal claim is just as forbidden as an unflattering one," adds "maintained a respectful tone" to the forbidden-example list, and gives the correct rewrite ("used respectful wording" / "used non-escalatory language").
2. **Explicit capability flag**: `VOCAL_EVIDENCE_AVAILABLE = false` (`src/lib/coaching/evidenceIntegrity.ts`) — a named, single source of truth for "no vocal metrics pipeline exists yet," instead of that fact being an unstated assumption baked into prose. Flips to `true` (and the check below starts trusting vocal claims) only once a real vocal-metrics feature exists — not yet, not in this change.
3. **Code-level validation, not just a prompt instruction**: `findParalinguisticViolation()` scans every text field of the generated evaluation (summary, each dimension's evidence/explanation, strengths, improvement areas, next_focus, comparison notes) for patterns implying audio evidence — tone, demeanor, calm(ly/ness), vocal, voice, volume, pace, pauses, hesitation, "emotional state," "sounded <adjective>". Deliberately does *not* ban the bare word "emotion" — acknowledging the *other person's* stated emotion in words ("I can see you're frustrated") is legitimate, transcript-based content central to several tools' own methodology; only a claim about the *speaker's own* perceived vocal/emotional state is the actual failure mode. `runEvaluation` (`src/lib/coaching/evaluationEngine.ts`) now runs this check whenever `VOCAL_EVIDENCE_AVAILABLE` is false (i.e. always, today): a violation triggers one additional regeneration attempt (mirroring the existing schema-retry pattern) with a targeted correction; if the regenerated output still violates, the whole evaluation is rejected (`EvaluationValidationError`) rather than ever being displayed — `/api/practice/end` already surfaces that as "couldn't generate reliable feedback, please try again," so no route changes were needed.

This is deliberately a second, independent layer — the round-1 fix relied entirely on the model following instructions; a probabilistic instruction failing twice in production is exactly why a deterministic check belongs in code, not only in the prompt.

No scoring, schema, weights, or feedback-layout changes.

## Evidence integrity: the Evaluation Engine was still generating vocal-delivery claims

Production kept producing claims like "The user maintained a calm demeanor throughout the conversation" and "User responded without raising their voice" — direct violations of the paralinguistic-safety guardrail added earlier, even though the coach is only ever given a text transcript.

**Root cause**: the guardrail sentence in `buildEvaluationSystemPrompt` (`src/lib/coaching/promptBuilder.ts`) was a *general* instruction, but several of the seeded `communication_tools` rows contained *specific, concrete* rubric text that directly asked the model to judge exactly the thing the guardrail forbade — a much stronger, more literal instruction that won out:
- `setting-a-boundary`'s Non-escalation criterion: `"Did the user stay calm and avoid turning the exchange into a conflict?"` — asks the model to judge "calm" directly. This is the smoking gun for the "calm demeanor" claim.
- `responding-to-aggression`'s core principle "Avoid mirroring the other person's volume or hostility" and common mistake "Matching the other person's hostility or volume" — "volume" is a literal audio measurement the coach doesn't have. This plausibly drove the "without raising their voice" claim.
- `responding-to-aggression`'s coaching guidance: `"Reward calm, brief responses..."`.
- `handling-criticism`'s core principle, step description, common mistake, and coaching guidance all used "tone" (`"...without accepting an unfair tone"`, `"...not just the tone"`, `"Arguing about tone..."`, `"...even if the tone stayed calm"`) — the tool's own methodology ("separate signal from delivery") is genuinely about not reacting to *how* something was delivered, but "tone" as written asks for a vocal judgment the coach can't make; the same idea is fully expressible as "framing"/"how it was phrased," which is visible in a transcript.

None of `giving-difficult-feedback` or `asking-open-questions` had literal violations, but their Non-escalation criteria were reworded too, for consistency, to anchor them explicitly to "the words used in the transcript" per the requirement to keep the Non-escalation dimension but make it explicitly transcript-based.

**Fix, two layers**:
1. **Data**: `supabase/seed.sql` rewritten (the fields above no longer use calm/tone/volume/demeanor language, and every tool's Non-escalation criterion is now explicitly "based on the words used in the transcript"). `supabase/migrations/0008_evidence_integrity_rubric_fix.sql` applies the same fix to already-seeded production data — each `update` is guarded by a `where` clause matching the exact old seeded value, so a row a coach has since customized via `/admin` (and so no longer matches) is left untouched rather than silently overwritten. **This migration must be run against the production Supabase project (`supabase db push`) for the fix to take effect there** — editing `supabase/seed.sql` alone only affects future fresh seeds, not the already-seeded live rows.
2. **Prompt, defense-in-depth**: `buildEvaluationSystemPrompt`'s guardrail now explicitly names "demeanor" alongside the existing tone/pace/pauses/confidence list, gives the exact two production sentences as forbidden examples, and — the important addition — states it *overrides anything above*: if a principle, common mistake, or evaluation criterion (Non-escalation included) is phrased using "calm," "tone," "voice," or "demeanor," the model must reinterpret it in terms of wording/language visible in the transcript, never assumed vocal delivery. This is the safety net for any future admin-authored tool that reintroduces this exact pattern without anyone noticing — the data fix alone wouldn't have covered that case.

No scoring, schema, weights, or feedback-layout changes — only the rubric *text* used to justify the Non-escalation dimension's judgment, and how the coach interprets it.

## Production fixes: the "stuck on Wrapping up…" hang, and the AI getting cut off at 0:00

Two production-confirmed bugs in the graceful-completion work below, fixed together since both live in `finishAndEvaluate()`.

- **The hang, root cause**: `/api/practice/end` returned 200 and evaluation was saved successfully — production logs confirmed no server-side error. The client code path after that success is exactly two lines: `dispatch({ type: "EVALUATION_COMPLETE" })` then `router.push(...)`. Neither can throw, so nothing ever reached the `catch` block — there was no error to show, just an app that looked frozen. The actual defect: (1) `stageLabel` had no case for the `"complete"` connection state, so it fell through to the same `"Wrapping up…"` string used for `"ending"`/`"evaluating"` — there was no way to visually tell "still working" from "done, just navigating," which is exactly what a user watching the screen would report as "stuck on Wrapping up"; and (2) `router.push()` from `next/navigation` is fire-and-forget — it returns `void`, not a promise, and surfaces no error or timeout if the background RSC fetch for the destination route stalls or fails. Combined, a slow or failed background navigation left the session screen showing the same "Wrapping up…" text forever, with nothing in the code that could ever notice or recover. Fix: `"complete"` now gets its own label ("Feedback ready — opening…"), `isEnding` now includes `"complete"` too so the screen can never flip back to showing live mic/text controls once the session is actually over, and a bounded 8s watchdog (`NAVIGATION_STALL_TIMEOUT_MS`) shows a "View feedback" button doing a hard `window.location.assign(...)` navigation — deliberately not `router.push()` again — the moment the component is still mounted that long after `router.push` was called. That button only re-reads the already-saved evaluation (the feedback page is a `force-dynamic` Server Component with no evaluation-triggering side effect), never re-runs it.
- **Structured finalization logging** (`src/lib/realtime/finalizationLog.ts`): every stage of ending a session — timer expired / End Practice requested, waiting for the current exchange or final transcription, realtime closed, transcript flushed, practice/end started/succeeded/failed, navigation started, navigation completed (logged from the component's unmount, since that's the only way to know navigation genuinely landed), navigation stalled — is now a `console.info` line with the session id and a timestamp, so a repeat of this incident is diagnosable from the browser console alone: whichever stage was logged last is where it stalled. No transcript text or other sensitive content is logged (see CLAUDE.md "Transcripts are sensitive").
- **The AI cutoff at 0:00, root cause**: timer expiry called the exact same immediate-stop path as manual End Practice — send `response.cancel`, then close the WebRTC connection — regardless of whether the AI was mid-sentence. `response.cancel` stops generation server-side and the subsequent `connection.close()` tears down the audio track locally, so any audio already streaming cut off mid-word. Fix: `finishAndEvaluate` now takes a `reason: "manual" | "timer"`. Manual End Practice keeps the old immediate-cancel behavior unchanged ("may remain an immediate explicit user stop"). Timer expiry instead calls `waitForCurrentExchangeToFinish` (`src/lib/realtime/exchangeCompletion.ts`) — a bounded (20s) poll of the connection state — before doing anything else, and never sends `response.cancel` at all: if the user is speaking, it waits for `USER_STOPPED_SPEAKING`; if that (or an AI turn already in progress) is followed by a response, it waits through `thinking`/`speaking` until the connection returns to `listening`; only then does closing happen, so nothing is interrupted. Once that exchange finishes, no new turn can start because the connection is closed immediately after — that's what "prevent another turn" means here, there's no separate mute step required.

## Graceful Realtime session completion + one Evaluation Engine safety guardrail

Two small, independently-scoped fixes on top of Realtime Phase 1 + 2 — no feedback format, scoring, or methodology changes.

- **Graceful completion** (`src/components/practice/realtime-simulation-client.tsx`, `src/lib/realtime/pendingTranscription.ts`): `finishAndEvaluate()` previously closed the WebRTC connection and posted to `/api/practice/end` synchronously, the instant End Practice was pressed or the timer hit zero. Two real gaps followed from that: (1) `appendMessage()` does a read-then-write to assign sequence numbers, and transcript POSTs are serialized through a client-side queue (`transcriptQueueRef`) — but `finishAndEvaluate` never awaited that queue, so a turn's transcript write could still be in flight when `/api/practice/end` read the transcript, silently dropping it from what the Evaluation Engine saw; (2) `server_vad` reports `input_audio_buffer.speech_stopped` before the corresponding `conversation.item.input_audio_transcription.completed` event arrives, so ending right as the user finished speaking could cut the connection before their final utterance was even transcribed, let alone persisted. The fix: on end, send `response.cancel` first (stop the AI from starting/continuing a turn), wait up to 4s (`waitForPendingUserTranscription`) for any in-flight user transcription to land, only then close the connection, then await the transcript queue before calling `/api/practice/end`. Bounded wait, not unbounded — a stalled or failed transcription (`conversation.item.input_audio_transcription.failed` is now handled too) can never block ending indefinitely. Timer/End Practice UX is otherwise unchanged; the "Wrapping up…" state already covered this window.
- **Evaluation Engine safety guardrail** (`src/lib/coaching/promptBuilder.ts`): added one explicit instruction to `buildEvaluationSystemPrompt` — the coach only ever receives a text transcript (no audio, no vocal/timing measurements), so it must never claim to have heard or observed tone of voice, pace, pauses, hesitation, confidence, nervousness, or any other paralinguistic/vocal signal, and must never describe *how* something was said, only what was said. This is a prompt-only change: no schema, scoring, or feedback-structure changes. It exists because Realtime voice makes it easy for the model to start narrating vocal delivery it was never actually given data about — that capability (timing/prosody capture) is explicitly future work (see the Realtime voice audit's Phase 4/5 in chat history), not implemented yet, so the coach must not claim it in the meantime.

## Realtime voice rollout (Phase 1 + 2): WebRTC, behind a rollback switch, batch path kept as fallback

Implements the audited "Option B" recommendation: the live interlocutor conversation moves to OpenAI's Realtime API over WebRTC (`src/lib/realtime/*`, `src/components/practice/realtime-simulation-client.tsx`), while the batch STT → LLM → TTS path (`src/lib/voice/*`, `src/components/practice/simulation-client.tsx`) is left completely untouched and still reachable.

- **Rollback switch**: `REALTIME_VOICE_ENABLED` (default off) plus a per-session escape hatch — `/practice/[sessionId]?voiceMode=batch` forces the batch component, and the Realtime screen itself offers a "Continue by text instead" link through that same URL the moment its WebRTC connection fails. Nothing about the batch path changes; it's the safety net until Realtime has been exercised in production.
- **Model**: `gpt-realtime-2.1` (confirmed present in the installed `openai` SDK's type union for `session.model`), overridable via `OPENAI_REALTIME_MODEL`.
- **Transport**: hand-rolled WebRTC, not the SDK's `openai/realtime/websocket` helper — the Node SDK only ships a WebSocket client; WebRTC's SDP offer/answer exchange is a plain browser `RTCPeerConnection` + one `fetch` per OpenAI's public WebRTC guide, confirmed against the SDK's own doc comments and the presence of a `client.realtime.calls` resource (`hangup`/`accept`/`refer`/`reject`, explicitly documented as covering "SIP or WebRTC" calls) even though call *creation* isn't itself exposed as an SDK method (the initiating POST carries a non-JSON `application/sdp` body, which is why it's a raw `fetch`, not a typed SDK call). The connect endpoint (`https://api.openai.com/v1/realtime/calls`) is the one part of this implementation inferred rather than directly observed in a working example — if the WebRTC handshake ever fails outright in testing, this is the first thing to check against current OpenAI docs.
- **Ephemeral credentials**: `client.realtime.clientSecrets.create()` mints a short-lived (`expires_after: 600s`) secret server-side, scoped with the full session config (model, instructions, voice, turn detection) baked in — `OPENAI_API_KEY` never reaches the browser, and the browser can't override the character/scenario instructions it's given.
- **Turn detection**: `server_vad` with `create_response: true` and `interrupt_response: true` — simpler and more predictable than `semantic_vad` for a first rollout, and `interrupt_response: true` is what makes the AI stop talking when the user starts, which the product brief's "feels like a live conversation" goal directly requires (this is baseline Realtime configuration, not the interruption *analytics* the brief explicitly deferred to a later phase).
- **Voice name**: separate `OPENAI_REALTIME_VOICE` env var (default `alloy`) rather than reusing `OPENAI_TTS_VOICE` — the Realtime voice list (`alloy, ash, ballad, coral, echo, sage, shimmer, verse, marin, cedar`) and the batch TTS voice list (`alloy, echo, fable, onyx, nova, shimmer`) only partially overlap; reusing the wrong one could silently pass an invalid voice.
- **Opening line stays verbatim and stays persisted the same way**: `startPracticeAction` still writes `scenario.opening_line` as the first `conversation_messages` row exactly as in the batch flow (unchanged). The Realtime session is then told, via a one-off `response.create` with a scoped `instructions` override ("Say exactly the following, word for word..."), to speak that same line — and its resulting transcript event is deliberately *not* persisted again (would duplicate row #1). Every later AI turn's transcript is persisted normally.
- **Transcript persistence race**: unlike the batch flow (one HTTP request per turn, inherently serialized), Realtime can emit the user's and the AI's transcript-completed events in quick succession over one data channel. `appendMessage()`'s sequence numbering is read-then-write and was never meant for concurrent writers (see the batch-era decision below). Rather than touch that shared helper, the Realtime client serializes its own writes through a promise chain (`transcriptQueueRef`) so only one `/api/simulation/realtime/transcript` call is in flight at a time per session.
- **Coach/interlocutor separation preserved structurally, not just by convention**: the Realtime session's `instructions` come from the exact same `buildInterlocutorSystemPrompt()` used by the batch engine — it has no access to methodology, evaluation criteria, or scoring. `/api/practice/end` and the entire `src/lib/coaching/*` evaluation engine are untouched; they read `conversation_messages` the same way regardless of which transport produced the rows.
- **Explicitly out of scope for this phase** (per the product brief's own phasing): Training Mode hints are not wired into the Realtime screen yet (the button simply isn't shown); no vocal/prosody analytics; no raw audio persistence; no interruption *tracking* beyond the state machine reflecting that the floor changed hands.

## Voice error handling: classify by category, not by HTTP status alone

Root cause of "the mic works once, then silently disappears": both voice routes collapsed every possible failure — no key configured, invalid key, expired quota, rate limiting, an unsupported model, a network blip, a malformed recording — into one generic `VoiceProviderError` mapped to HTTP 503, and the client treated *any* 503 as "voice was never configured," permanently setting `voiceAvailable = false` for the rest of the session. Worse, a failed TTS call had no user-facing message at all — it silently fell back to text, so the only visible symptom was the mic icon vanishing.

Fixed by giving `VoiceProviderError` a closed `VoiceErrorCode` (`src/lib/voice/types.ts`), classifying real OpenAI SDK errors into it via `src/lib/voice/errorClassification.ts` (status code alone isn't enough — OpenAI reuses HTTP 429 for both true rate limiting and quota/billing exhaustion, distinguished only by the response body's `code`/`type` field), and centralizing user-facing message + HTTP status per code in `src/lib/voice/errorResponse.ts`. Critically, the client (`simulation-client.tsx`) now only disables voice for the rest of the session when the server reports `code: "not_configured"` — every other category (invalid key, quota, rate limit, model, permission, network, unknown) surfaces a clear message via the existing error banner and leaves the mic enabled for the next attempt. Server-side, each OpenAI provider catch block logs the classified category, HTTP status, provider error code, and OpenAI request ID — never the API key, never audio/transcript content — so failures are diagnosable from Vercel logs alone.

## Practice setup route moved to `/practice/setup/[scenarioId]`

Originally the setup screen lived at `/practice/[scenarioId]/setup`, alongside `/practice/[sessionId]` and `/practice/[sessionId]/feedback`. Next.js requires every dynamic segment at the same position in the route tree to share one parameter name, so having both `[scenarioId]` and `[sessionId]` directly under `/practice/` throws `You cannot use different slug names for the same dynamic path` at runtime — `next build` didn't catch it, but `next start` did on the first real request, caught during this build's own smoke test. Moving setup under a static `setup/` segment (`/practice/setup/[scenarioId]`) puts it in a different subtree from `/practice/[sessionId]`, resolving the collision without changing either ID's meaning.

## Supabase packages pinned below `latest` (`@supabase/supabase-js@2.45.x`, `@supabase/ssr@0.5.x`)

`npm install @supabase/supabase-js@latest` initially pulled in a very recent rewrite of `@supabase/postgrest-js`'s generic type system (requiring `Database` to carry `__InternalSupabase`, per-table `Relationships`, and an internal, unexported `GenericSchema` shape). Under that system, a hand-written `Database` type structurally equivalent to the standard Supabase-CLI-generated shape produced `never` types on every `.insert()`/`.update()` call and even on some `.select()` field access, for reasons that didn't resolve to a documented cause after investigation. Rather than keep debugging an internal, seemingly-in-flux type-inference path, `@supabase/supabase-js` and `@supabase/ssr` are pinned to the long-established 2.45.x / 0.5.x line, which uses the classic, extensively documented `{ public: { Tables: { table: { Row, Insert, Update } } } }` shape our `src/lib/db/types.ts` follows and which every current Supabase+Next.js tutorial matches. Revisit this pin (and drop the hand-written types in favor of `supabase gen types typescript`) once a real Supabase project exists and the newer typegen path has stabilized/documented itself.

## Playwright browser: use pre-installed Chromium, don't run `playwright install`

The execution environment has Chromium pre-installed at `/opt/pw-browsers` with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`. The e2e config uses that path rather than triggering a download. Document this for anyone running e2e tests in a different environment: run `npx playwright install chromium` there first.

## AI provider: OpenAI, behind an `AIProvider` interface

OpenAI was chosen as the default concrete implementation because it has one SDK covering chat/structured-outputs, transcription (Whisper), and TTS, minimizing the number of vendor accounts needed to get the MVP fully working. The application never calls the OpenAI SDK outside `src/lib/ai` and `src/lib/voice` — swapping to Anthropic/Google/ElevenLabs/Deepgram later means writing one new file per provider and changing the factory, not touching simulation/coaching logic. No credentials were supplied during this build, so `OPENAI_API_KEY` is unset by default and the app runs against `MockProvider`s — documented in `.env.example` and `/docs/STATUS.md`.

## No credentials available at build time → automatic Mock fallback, not a hard failure

Per the build brief (section 25), missing provider credentials must not block building the full loop. `src/lib/ai/index.ts` and `src/lib/voice/index.ts` construct a deterministic Mock implementation whenever the relevant API key env var is absent, and the UI surfaces this (a small "running in demo mode" indicator) rather than silently pretending mock output is a live model or real audio. This keeps `npm run build`, the Playwright e2e test, and manual review of the whole flow possible with zero external accounts.

## Voice transport: turn-based HTTP, not realtime streaming

Given Vercel's stateless serverless execution model and the MVP's emphasis on reliability over cutting-edge latency (section 22, section 70), voice uses `MediaRecorder` → `/api/voice/stt` → text → `/api/simulation/respond` → text reply → `/api/voice/tts` → `<audio>` playback, all as discrete request/response calls. No WebSocket/WebRTC server component is built. A `RealtimeVoiceProvider` slot is documented in the architecture doc for a future streaming upgrade (e.g., OpenAI Realtime API with short-lived client secrets minted server-side) without a rewrite.

## Auth: Supabase email/password only, no third-party OAuth

Keeps the MVP shippable without registering OAuth apps with Google/Apple/etc. (each of those is its own account-creation and review process, out of proportion for an MVP). Supabase Auth still gives us session handling, RLS integration (`auth.uid()`), and a clean upgrade path to add OAuth providers later purely as additional sign-in buttons.

## Database: hand-written SQL migrations + hand-written TypeScript types, no ORM

Prisma/Drizzle would add a dependency and a generated-client build step for a schema of six tables. Plain SQL migrations under `supabase/migrations` plus a single hand-maintained `src/lib/db/types.ts` keep the stack simple (principle: avoid unnecessary dependencies) while still giving full type safety at the `src/lib/db/*` query-function boundary, which is the only place raw Supabase calls happen.

## JSONB usage: only for genuinely variable-length/structured lists

Fields like `core_principles`, `character_behaviours`, `escalation_rules`, evaluation `strengths`/`improvements`, and `structured_evidence` are stored as JSONB because they're variable-length structured lists with no query/filter requirement of their own — normalizing them into child tables would add joins and CRUD ceremony with no product benefit at this scale. Everything with a clear scalar shape (scores, names, slugs, weights-as-a-flat-object) is a real column. This follows the brief's instruction not to use JSON as a substitute for schema design, while still using it where it demonstrably helps (tool/scenario authoring flexibility for the coach).

## Evaluation weights: flat JSON object of six numeric weights, tool-level default + optional scenario override

Stored as `evaluation_weights jsonb` on `communication_tools` (`{ clarity, assertiveness, acknowledgment, non_escalation, technique, effectiveness }`, expected to sum to 1.0) with an optional partial override at `scenarios.evaluation_overrides.weights`. The evaluation engine merges scenario-over-tool at read time. Validated with zod before use; if weights don't sum to ~1.0 (tolerance for rounding) they're renormalized rather than erroring, since a coach hand-editing weights in the admin UI shouldn't be able to break scoring for existing content.

## Six evaluation score columns + one JSONB evidence blob, not eighteen columns

Section 41 suggests six `*_score` integer columns on `evaluations`. Per-dimension evidence and explanation text are always read/written together with the scores as one structured unit (never queried independently), so they live in `structured_evidence jsonb` keyed by dimension rather than as twelve more columns. This mirrors the AI's structured output shape directly, simplifying validation and persistence.

## Next.js version: pinned to 15.x, not the 16.x that `create-next-app@latest` installs

`create-next-app@latest` currently scaffolds Next.js 16, which ships an auto-generated `AGENTS.md` explicitly warning that it has breaking changes not reflected in model training data. Given the size and correctness-sensitivity of this build (auth middleware, streaming route handlers, server actions across dozens of files), the safer choice was Next.js 15 — stable, extensively documented, and what this implementation has high confidence in getting right on the first pass. Revisit once 16 has been out long enough to have reliable documentation/community patterns.

## Component library: hand-rolled shadcn-style primitives, not the shadcn CLI

The shadcn CLI is interactive and pulls in Radix primitives per component. For the MVP's actual component surface (button, card, input, textarea, select, badge, dialog-ish sheet, tabs, slider), hand-writing them once in `src/components/ui` using `clsx`/`tailwind-merge`/`class-variance-authority` gets the same restrained visual language with fewer dependencies and no CLI/network dependency during build. Can be migrated to the real shadcn CLI later with minimal disruption since the API shape is intentionally similar.
