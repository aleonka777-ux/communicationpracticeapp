## Realtime voice (Phase 1 + 2) — just added

- Full architecture in `docs/DECISIONS.md` ("Realtime voice rollout") and `docs/ARCHITECTURE.md` §9.2.
- **Off by default** — set `REALTIME_VOICE_ENABLED=true` in Vercel (alongside the already-configured `OPENAI_API_KEY`) to turn it on. Until then, every session uses the existing batch STT/TTS path unchanged.
- Not yet exercised against a live OpenAI Realtime session in this build environment (no browser with microphone access here) — the one part of the implementation genuinely unverified end-to-end is the WebRTC SDP exchange against `https://api.openai.com/v1/realtime/calls`, which was inferred from the installed SDK's types/doc comments rather than observed working. First real test should specifically watch for this.
- **Graceful session completion**, added just after Phase 1 + 2: ending (timer or End Practice) waits for the user's last utterance to finish transcribing and flushes queued transcript writes before `/api/practice/end` runs — see `docs/DECISIONS.md` for the two races this closes.
- **Evaluation Engine safety guardrail**, added at the same time: the coach prompt now explicitly forbids claiming to have observed tone, pace, pauses, confidence, or any other paralinguistic/vocal signal, since only a text transcript is ever provided. No scoring, schema, or feedback-format changes — the full rubric/methodology redesign is still future work (Communication Manual / content architecture, not started).
- **Two production-confirmed fixes**, added after live testing surfaced them: (1) the practice screen could get stuck showing "Wrapping up…" indefinitely even after evaluation had already succeeded server-side, because `"complete"` had no distinct UI state and `router.push()` cannot report a stalled navigation — fixed with a distinct "Feedback ready" label plus a bounded watchdog that offers a "View feedback" recovery button (hard navigation, doesn't re-run evaluation); (2) the AI's voice was being cut off mid-word when the timer hit 0:00, because timer expiry used the same immediate-cancel path as manual End Practice — fixed so timer expiry now waits for the current exchange to finish naturally before ending (manual End Practice is unchanged). Every finalization stage is now logged client-side for future diagnosis. See `docs/DECISIONS.md` "Production fixes" for the full detail.
- **Evidence-integrity fix**, added after production still generated "maintained a calm demeanor" / "without raising their voice" despite the earlier guardrail: the real cause was seeded rubric text (`evaluation_criteria`, `coaching_guidance`, `core_principles`, `common_mistakes`) that literally asked the coach to judge "calm," "tone," or "volume." Fixed in `supabase/seed.sql` plus a guarded production migration (`0008_evidence_integrity_rubric_fix.sql` — **must be run against the live Supabase project, e.g. `supabase db push`, for existing seeded rows to pick up the fix**), and the prompt builder's guardrail now explicitly overrides any rubric text phrased that way in the future too.
- **Evidence-integrity fix, round 2**, added after production generated "maintained a respectful tone…" — a claim never sourced from any rubric text (verified against both the original and corrected seed content); the prompt guardrail's forbidden-example list had only covered negative-sounding vocal claims, so a flattering one like "respectful tone" slipped through. Since a prompt instruction alone had now failed twice in production, added an actual code-level enforcement layer: `VOCAL_EVIDENCE_AVAILABLE = false` (`src/lib/coaching/evidenceIntegrity.ts`) plus `findParalinguisticViolation()`, run inside `runEvaluation` — any paralinguistic claim in the generated evaluation triggers one regeneration attempt.
- **Evidence-integrity fix, round 3**, added after production confirmed round 2's detection worked but its recovery was too destructive: a violation surviving one regeneration attempt rejected the *entire* evaluation (502), so a user who completed a real session lost all feedback over one leftover word in one field. Fixed by sanitizing instead of rejecting: `sanitizeEvaluationOutput()` rewrites only the still-violating field(s) — a meaning-preserving phrase rewrite where a safe one exists ("respectful tone" → "respectful wording", etc.), otherwise a short neutral transcript-grounded statement for that field alone. `/api/practice/end` now completes successfully in this case instead of 502ing. See `docs/DECISIONS.md` "Evidence-integrity recovery, round 3" for full detail.
- **Acoustic-echo false-interruption fix**, added after production reports of the AI's speech suddenly stopping (UI flipping to Listening with no one speaking) on laptop/phone speakers but never over headphones — a clear echo signature. Root cause: `interrupt_response: true` cancels the AI's response server-side the instant a single VAD `speech_started` event fires, with no minimum-duration check possible from the client. Fixed with explicit mic constraints (echoCancellation/noiseSuppression/autoGainControl, applied settings verified via `track.getSettings()`), a moderate VAD threshold increase (0.5 → 0.6), and — the actual fix — `interrupt_response` disabled in favor of a new client-side confirmation window (`src/lib/realtime/bargeIn.ts`, 250ms): a blip that stops within the window never touches the AI's response at all, while sustained genuine speech still interrupts it promptly. Structured debug logging (`src/lib/realtime/debugLog.ts`) now distinguishes echo/blips from real barge-in.
- **Startup-specific false-interruption fix**, added after that same fix left a handful of false interruptions clustered only at the very start of the conversation over speakers (none over headphones, none later once things settled) — a pattern that specifically rules out the VAD threshold as the cause, so it stayed at 0.6. Two compounding, genuinely startup-specific factors: (1) a real state race, since the barge-in controller only learned "the AI is speaking" from `output_audio_buffer.started`, which isn't guaranteed to be processed before the AI's audio (a different transport) actually reaches the speaker — fixed by also treating `response.created` (which OpenAI's docs confirm always precedes audio) as "speaking," with `response.done` as the backstop that clears it; (2) the browser's echo-cancellation filter is least converged during the very first turn, since it has nothing to adapt against until output begins — fixed with a widened (500ms vs. the normal 250ms) confirmation window scoped only to that first turn, reverting to normal immediately after.
- **Startup false-interruption fix, round 2**, added after a screen recording reproduced the false interruption again with a concrete timeline confirming the false `speech_started` began at or near when AI audio itself started and persisted well past the round-1 fix's flat 500ms window. Replaced the flat window with `src/lib/realtime/startupGuard.ts`'s `computeStartupConfirmMs` — a continuous grace-period formula anchored to actual AI audio start (1000ms grace + 500ms follow-up right at playback start, shrinking as real time passes, collapsing to the same 500ms round 1 used once the grace period fully elapses). Still no VAD threshold change (0.6), no muting, no delay outside the one first turn. See `docs/DECISIONS.md` "Startup false interruptions, round 2" for full detail, including why a flat larger window for the whole first turn was rejected in favor of a time-anchored one.
- Known, deliberate gaps for this phase: Training Mode hints aren't wired into the Realtime screen; no vocal/prosody analytics; no raw audio persistence.
- **Realtime timing + interruption metrics (measurement layer)**, added once the above stabilized: `src/lib/realtime/sessionTimeline.ts` captures objective per-turn timing from Realtime SDK events (server-authoritative `audio_start_ms`/`audio_end_ms` for user turns, client-clock `output_audio_buffer.started`/`.stopped` for AI turns) and derives session-level metrics (turn counts, speaking time/percentage, overlap, confirmed-interruption count, user/AI response latency) at `finalize()`. New additive migration `0009_realtime_timing_metrics.sql` (`realtime_turn_events`, `realtime_session_metrics`, both RLS-protected) persisted via a new `/api/simulation/realtime/metrics` route, called best-effort from `finishAndEvaluate` — a metrics failure is logged and never blocks the transcript/evaluation flow. No raw audio is stored; only timestamps, durations, and transcripts already persisted elsewhere. Confirmed barge-in (not raw VAD events) is the only signal counted as an interruption; overlap is tracked separately. `VOCAL_EVIDENCE_AVAILABLE` stays `false` — these metrics do not feed the Evaluation Engine yet. Dev/QA visibility only (`console.debug`), no production UI. See `docs/DECISIONS.md` "Realtime timing metrics" for the full event-source audit and design.
- **Measurement-integrity fix**, caught before migration `0009` was ever applied to production: every raw `speech_started`/`speech_stopped` pair — including known false echo-triggered blips — was being counted as a real user turn, contaminating turn count, speaking time, avg/longest duration, both response-latency metrics, and overlap. Fixed with an evidence-based classification (`"confirmed"` vs `"suspected_noise"`) using confirmed-barge-in state, transcript presence/emptiness, explicit transcription failure, and duration only as a last resort — see `docs/DECISIONS.md` "Realtime timing metrics, measurement-integrity fix." `0009` was edited in place (not superseded) since it hadn't shipped yet; still a single `supabase db push` to apply.
- **Production persistence bug, fixed**: `0009` (now applied to production) declared several timing columns `integer`, but `sessionTimeline.ts`'s values are `performance.now()`-derived and inherently fractional — every `/api/simulation/realtime/metrics` call failed with Postgres `22P02` (`invalid input syntax for type integer: "16258.5"`), leaving both timing tables permanently empty. Fixed with additive migration `0010_fix_realtime_metric_numeric_types.sql` (`ALTER COLUMN ... TYPE double precision`) — counters (`user_turn_count`, `ai_turn_count`, `overlap_count`, `confirmed_interruption_count`, `suspected_noise_event_count`, `turn_index`) stay `integer`. Validation schema + DB-row mapping moved to `src/lib/realtime/metricsPayload.ts` for direct unit testing. **Requires `supabase db push` in production** — see `docs/DECISIONS.md` "Realtime timing metrics, numeric type fix."
- **Measurement-integrity fix**: a confirmed barge-in landing in the gap between `response.created` and `output_audio_buffer.started` (the response was still being generated, hadn't produced audio yet) was recording `aiResponseId: null` instead of naming the response it interrupted — zero overlap in that case is correct (no audio ever played), but the attribution was missing. Fixed with `recordResponseCreated()` tracking a pending (created-but-not-playing) response as a fallback attribution target; no phantom AI turn is fabricated. See `docs/DECISIONS.md` "confirmed barge-in with zero overlap."
- **Product-semantics fix**: "technical confirmed barge-in" (the controller cancelled a response) and "audible user interruption" (the user spoke over AI audio actually playing) are now explicit, separate concepts — a pre-playback cancellation no longer inflates the coaching-facing `confirmed_interruption_count`; a new `technical_barge_in_count` holds the raw diagnostic total. New migration `0011_barge_in_context.sql`. See `docs/DECISIONS.md` "technical confirmed barge-in vs. audible user interruption."
- **AI turn lifecycle fix**: production's first multi-turn session showed AI speaking time at 153% of session duration, 50s of spurious overlap across 7 events, and a duplicated interruption count. Root cause: `response.cancel` alone never drains the output audio buffer, so an interrupted AI turn's `output_audio_buffer.stopped` could arrive very late or never — leaving it open until finalize, where it got closed with the full session's elapsed time, inflating speaking time/overlap and hiding it from response-latency lookups (forcing latency against a stale, unrelated turn instead). Fixed by also sending/handling `output_audio_buffer.clear`/`.cleared`, plus a `response.done`-based safety net for non-completed statuses. The duplicated interruption count shared the same root cause; a confirmed barge-in is now explicitly idempotent per interrupted AI response. New structural invariant check (`validateSessionTimelineInvariants`, logged, never used to clamp values) added to catch a recurrence immediately. New migration `0012_ai_turn_lifecycle_and_idempotent_interruption.sql`. See `docs/DECISIONS.md`.
- **Classification-timing fix**: the next control test (one deliberate, audible interruption) still came back as 0 coaching interruptions and 0.8ms of overlap. Root cause: audible-vs-pre_playback classification and attribution were computed by reading AI state live at confirmation time (250ms–1.5s after speech started), not at the moment the interruption actually began — by confirmation time the AI's turn could already have closed for an unrelated reason. Fixed by snapshotting the AI's playing/pending response id onto the user turn at `speech_started` time and reading that snapshot at confirmation time instead of live state. Overlap/latency were re-verified to already use only the client monotonic clock end to end — no cross-clock bug found there; the near-zero overlap was a downstream symptom of the same misclassification. Also fixed a second, independent bug found during this audit: a reconnect never reset the previous `bargeIn` controller, so a stale pending confirmation timer could fire later and record a spurious event. New migration `0013_audible_ai_response_id_at_start.sql`. See `docs/DECISIONS.md`.
- **Media/data-channel ordering race, part two**: the next control test still showed 0 coaching interruptions and ~0.5ms overlap across 2 events. Root cause: WebRTC media (actual audio) and the Realtime data channel (`output_audio_buffer.started`) are separate transports with no guaranteed relative ordering — the audio can reach the user's speakers moments before `.started` is processed, so even the at-start snapshot could read "not yet playing." Audited `<audio>` element playback events (`playing`/`waiting`/`pause`) as an authoritative alternative — not usable, since OpenAI's output track is one continuous stream reused across turns, so those events track connection health, not per-turn silence. Fixed with a bounded, documented reconciliation resolved at `finalize()` time: a pending response whose `.started` lands within 100ms after speech began is treated as the same event reported a few ms apart by two transports and reclassified audible; a response starting well outside that window (a true pre-playback case) is left alone. Also added a 10ms minimum-meaningful-overlap floor, filtering out event-processing-order artifacts (the reported ~0.5ms) at the source. No new migration — only computation timing changed. See `docs/DECISIONS.md`.
- **AI audible-end measurement limitation, documented (no code change)**: investigated why a deliberate mid-speech interruption in one control session showed only a ~0.4ms overlap. Root cause: `output_audio_buffer.stopped` is a server-side "buffer drained" signal, not proof the client's WebRTC jitter buffer has finished rendering — the true audible tail can extend past it by an unmeasured amount, and no reliable per-response browser playback-end signal exists given the continuous remote `MediaStream`. No compensating end-side tolerance was added (would be exactly the arbitrary padding this measurement layer avoids) — documented as a known boundary limitation instead. See `docs/DECISIONS.md`.
- **Phase 4A — speech-delivery evidence** (speaking rate, intra-utterance pauses, filler/disfluency candidates, relative vocal intensity): a new, separate evidence-collection layer, explicitly NOT feeding scoring/coaching interpretation yet (`VOCAL_EVIDENCE_AVAILABLE` stays `false`). Audited the current Realtime transcription pipeline first: `whisper-1`, no word-level timestamps, no verbatim/disfluency-preserving mode — vocal disfluency (`um`/`uh`) evidence is therefore explicitly best-effort/undercount-only, while lexical/discourse candidates (`like`, `well`, `you know`, etc.) and immediate-word-repetition are more reliable (real words survive Whisper's smoothing). Speaking rate (WPM) and filler/disfluency candidates are derived from data the timing layer already has (transcript + turn duration) in `sessionTimeline.ts` + the new pure `fillerCandidates.ts`. Intra-utterance pauses and relative (never dB SPL) vocal intensity require live audio, added via a new pure, testable `speechDeliveryTracker.ts` (adaptive per-session noise-floor pause detection, 250ms minimum-pause threshold) fed by a thin browser-only `micEnergyMonitor.ts` (Web Audio `AnalyserNode` on the LOCAL mic stream only — never the remote AI audio, never `audioContext.destination`). All candidates are stored `unclassified` — never scored, never labeled "filler"/"strategic"/"hesitant". New additive migration `0014_speech_delivery_evidence.sql`. No raw audio persisted anywhere — only scalar counts/rates/positions/relative-intensity numbers. Dev/QA visibility only (`console.debug` via `speechDeliveryDebug.ts`), no production UI. See `docs/DECISIONS.md` "Phase 4A: speech-delivery evidence."
- **Phase 4A pause timestamp clock-origin fix**: the first production dataset showed every `realtime_pause_events.start_ms` offset from its owning turn by a constant ~48.8s. Root cause, verified from code: `sessionTimeline.ts` zeroes itself at construction (`sessionStartMs`/`elapsed()`), but `speechDeliveryTracker.ts` had no equivalent anchor and persisted raw, un-anchored `performance.now()` (page-navigation-relative, not session-relative) directly as pause timestamps — not an `AudioContext.currentTime` mismatch (the mic-energy monitor never produces a timestamp at all). The offset equaled however long the page had already been open before the practice screen mounted. Duration and `position_ratio` were already correct (both are differences/ratios, so a constant additive offset cancels out) — only the absolute `start_ms` was wrong. Fixed by giving `speechDeliveryTracker.ts` its own session-relative zero point at construction, mirroring `sessionTimeline.ts` exactly — no hardcoded offset. Added `validatePauseClockOrigin()` (`mergeSpeechDeliveryEvidence.ts`) as a diagnostic-only regression guard (range/tolerance/position-ratio-consistency checks, never clamps). No migration needed — schema was already correct. See `docs/DECISIONS.md`.
- **Response-stall incident**: production showed "Thinking" stuck for ~43-45s after `user_turn 8`, with the stall then silently recorded as `longest_user_response_latency_ms = 45152.4` — blaming a system non-response on the user. Root cause: the latency-pairing algorithm scanned arbitrarily far back for "the most recent preceding AI turn," so when a genuinely adjacent AI turn was correctly excluded for a 0.4ms overlap, the algorithm paired the STALE AI turn with a much later, unrelated user turn instead of leaving it unpaired. Fixed with strict conversational-adjacency pairing over a merged chronological timeline — only immediately-adjacent, non-overlapping AI/user pairs ever produce a latency value; nothing is ever reassigned to a later turn. The stall itself is now captured as new, explicitly non-coaching evidence (`unansweredUserTurnCount`/`longestUnansweredStallMs`). Also fixed: `connectionState.ts` could leave the UI stuck in "Thinking" indefinitely, since `response.done`/`error` never dispatched any transition — added one lifecycle-proven `thinking → listening` transition (only when a response definitively concludes without producing audio) plus a 12s watchdog (reveals the text-fallback recovery affordance; never an automatic retry, since no Realtime state-query capability exists to rule out a duplicate response). Phase 4A's `openTurn`/`closeTurn`/`pushEnergySample` calls are now routed through a small `safeCall()` helper for guaranteed failure isolation, audited but not found to be the incident's cause. New migration `0015_response_stall_evidence.sql`. See `docs/DECISIONS.md`.
- **State-machine race: Thinking shown during audible AI playback**: a different production incident (NOT a stall — `unanswered_user_turn_count = 0`) showed the AI responding normally and audibly while the UI still said "Thinking." Root cause, verified against `connectionState.ts`: the AI genuinely started speaking while the user's own turn was still in progress (production: `ai_turn 8` began 682.8ms after `user_turn 9` started and 46.7ms before it ended); the `user_speaking` state had no transition rule for `AI_STARTED_SPEAKING` at all (silently dropped), and its only rule for `USER_STOPPED_SPEAKING` was unconditional (`→ "thinking"`, with no check of whether AI audio was already playing). Fixed with two changes resolved from real concurrent evidence, never a timeout: added `user_speaking: { AI_STARTED_SPEAKING: "speaking" }` for real-time accuracy while the user is still mid-turn, and a new optional `aiSpeaking` field on the `USER_STOPPED_SPEAKING` event (backed by a new `aiAudioPlayingRef`, tracking actual `output_audio_buffer.started`/`.stopped`/`.cleared` state — deliberately distinct from `bargeIn.ts`'s own broader flag) that makes the reducer resolve to `"speaking"` instead of `"thinking"` when AI audio is confirmed already playing. No VAD/turn-segmentation change, no changes to stall detection or the 12s watchdog. No migration — pure client-side state-machine fix. See `docs/DECISIONS.md`.
- **Navigation-latency fix**: production showed `/api/practice/end` succeeding, `router.push()` firing immediately, then 8.464 seconds stuck on "Wrapping up…" before the feedback page rendered — with `navigation_completed` logged just 62ms after the 8s watchdog's `navigation_stalled`. Verified from code (not assumed) that this was NOT the watchdog rescuing a stuck navigation: the fallback required an explicit manual button click, and a human reacting within 62ms is implausible — the original `router.push()` was independently resolving around the same time. Real cause: `feedback/page.tsx` (`force-dynamic`) awaited two independent Supabase reads (`getSessionWithContext`, `getEvaluationForSession`) sequentially despite `/api/practice/end` having already persisted both moments earlier, layered on top of the shared `(app)/layout.tsx`'s own re-run auth+profile fetch and the page's own defensive re-auth check (every navigation in this dynamic route tree re-executes the whole chain — a single slow link anywhere in it, plausible right after a long voice session, explains an outlier this large). Fixed by parallelizing the one genuinely-independent pair of reads via `Promise.all`, and by upgrading the existing manual-click hard-navigation fallback to fire automatically once the watchdog elapses (still shown as a visible backstop) — safe because `/api/practice/end` is independently idempotent (returns the existing evaluation immediately on a repeat call) and the new `navigationRecovery.ts` module extracted for this fix structurally cannot call it at all (its only capabilities are navigate/navigate/notify). `NAVIGATION_STALL_TIMEOUT_MS` left at 8000 — no evidence here justified retuning it. No migration. See `docs/DECISIONS.md`.

## Completed

- **Phase 1 — Foundation**: Next.js 15 + TypeScript (strict) + Tailwind v4 project; Supabase client wrappers (browser/server/admin) and auth-refresh middleware; full SQL schema (`profiles`, `communication_tools`, `scenarios`, `practice_sessions`, `conversation_messages`, `evaluations`) with RLS policies on every table; email/password auth (signup/login/logout); responsive app shell (top bar + bottom nav, safe-area aware); communication tool library + scenario browsing; seed data (5 tools × 2 scenarios, `supabase/seed.sql`); coach/admin CRUD for tools and scenarios.
- **Phase 2 — Text practice loop**: practice setup screen; `AIProvider` interface with OpenAI + deterministic Mock implementations; simulation prompt builder/engine (Realistic Mode, character stays in-character, never coaches); explicit conversation state machine; 2/3/5-minute timer (default 3); turn-based `/api/simulation/respond`; End Practice (manual + timer-triggered); coaching/evaluation engine with a zod-validated structured-output schema and one controlled retry on validation failure; six practice indicators with evidence; feedback UI (overall result, what worked, what could improve, next focus); Try Again with correct attempt numbering; attempt comparison against the previous completed attempt.
- **Phase 3 — Voice**: `SpeechToTextProvider` / `TextToSpeechProvider` interfaces with OpenAI (Whisper + TTS) and Mock implementations; `/api/voice/stt` and `/api/voice/tts` route handlers; `MediaRecorder`-based mic capture with permission-denial handling; TTS playback of every interlocutor line (opening line included) when available; typed input always available as a fallback, and the default when voice is unavailable.
- **Phase 4 — Training Mode**: Realistic/Training selector on the setup screen; "Need a hint?" control (Training Mode only) that pauses the simulation, calls the coach layer for one short suggestion, and resumes with state preserved; `hint_count` tracked per session and factored into the evaluation prompt.
- **Phase 5 — History & repeat practice**: session history list; reopening a session shows the transcript, scores, feedback, and comparison (or a "not completed" state with a resume/delete option); delete-own-session; "Practice this again" from both history and the feedback screen; self-reported readiness (1–5) captured after feedback, stored independently of AI scoring.
- **Phase 6 — Mobile/PWA polish**: mobile-first layout throughout (44px+ touch targets, safe-area insets, no forced viewport zoom lock); loading/empty/error states audited (`src/components/ui/state.tsx`, segment-level `loading.tsx`/`error.tsx`, a root `global-error.tsx`); basic PWA manifest + SVG icon; production build verified.
- **Testing**: 56 Vitest unit tests across timer math, the full state-machine transition table, weighted scoring, attempt numbering/previous-attempt selection, score-delta comparison, AI-output schema validation, admin form parsing, and an authorization test exercising `requireOwnedSession` (401 unauthenticated, 404 cross-user, 404 missing, success for the owner) against a stubbed Supabase client. One Playwright e2e test covering the full happy path (signup → choose skill → choose scenario → practise → end → feedback → try again) with the AI provider mocked.

## Known limitations

- **No live Supabase project was connected during this build session.** The schema, RLS policies, and seed data exist as SQL and have been reviewed carefully, but have not been applied to or exercised against a real Postgres instance from here. `npm run build` passes using placeholder env values that satisfy validation but point at no real backend. A production (`next start`) smoke test against those placeholder values did confirm: the app boots, unauthenticated requests to protected routes (`/home`, `/admin`) correctly redirect to `/login` via middleware, and the login/signup pages, manifest, and icon all render — i.e. everything that doesn't require a working Supabase connection behind it. That smoke test is also what caught and fixed a real route-collision bug (see `docs/DECISIONS.md` "Practice setup route moved").
- **No OpenAI (or other) API key was supplied.** The app runs entirely on its deterministic Mock `AIProvider`/`SpeechToTextProvider`/`TextToSpeechProvider` by default (see `docs/DECISIONS.md`). Real conversation quality, transcription accuracy, and speech synthesis have not been evaluated against the live API — only that the request/response plumbing and structured-output validation path are correct against a hand-authored JSON Schema.
- **The Playwright e2e test has not been run in this session** for the same reason (no live Supabase project to sign up against). It's written and wired into `npm run test:e2e`, targeting the pre-installed Chromium in this environment; it needs a real (or local `supabase start`) test project with migrations + seed applied to actually execute.
- **Supabase package versions are pinned below `latest`** (`@supabase/supabase-js@2.45.x`, `@supabase/ssr@0.5.x`) due to a type-inference issue in the newest release — see `docs/DECISIONS.md`.
- Coach → `role = 'coach'` promotion is a direct SQL step (documented in the README), not an in-app flow, to avoid building self-service privilege escalation for an MVP with presumably one or a handful of coaches.
